# 设计：数据库数据按需加载与页内虚拟渲染

> 状态：待确认，确认后实施
> 日期：2026-10-15
> 需求原文（用户）：「数据多时默认一页显示 10 条，剩下的不加载，翻页再加载？降低内存」
> 关联：`doc/分析-全项目性能热点与优化方案.md` §九（内存剖析）

---

## 一、现状核实（先澄清一个前提）

| 项 | 现状 | 结论 |
|---|---|---|
| 表数据加载 | MySQL 走服务端分页 LIMIT/OFFSET（mysql.js:171-183），Redis 走 SCAN 游标（redis.js:151） | **"剩下的数据不加载"已经成立**——任何时刻只取当前页（≤100 行），不会整表进内存 |
| 每页行数 | PAGE_SIZE = 100（db-session.jsx:21），写死 | 可优化点 ① |
| 页内渲染 | antd Table 把当前页 100 行全部渲染成 DOM（每行含高亮 span 树/编辑态） | 可优化点 ②（真正内存点） |
| Redis 大 hash/list 详情 | hgetall/lrange 一次取上限 1000 行全量渲染 | 可优化点 ③（redis 侧最大内存点） |
| antd 能力 | 6.5.1 的 Table 支持 virtual 属性（InternalTable.js:423 → RcVirtualTable，需配合 scroll.y——DbGridTable 已传 y） | 页内虚拟渲染的现成抓手 |

### 内存收益的诚实评估

renderer 私有总量 142MB 中，表格 100 行 DOM 约占 2~5MB（每行单元格含 React 节点/高亮 span）。把每页 100→10 条的直接内存收益只有 1~4MB，占比很小；真正的价值排序：

1. **页内虚拟渲染（virtual）**：DOM 行数与 pageSize 解耦——pageSize 100/500 时 DOM 始终只有可视区 ~20 行，内存低 + 长列表滚动流畅，收益最大且不牺牲翻页体验
2. **Redis 大 hash 详情 1000 行**：一次 hgetall 的 1000 行 DOM 才是 redis 侧真正的内存点（估计 20~50MB），改分批加载收益实在
3. **每页行数可配置**：交互 vs 内存的权衡交给用户，默认值不建议激进到 10（100 万行的表要翻 10 万次页）

## 二、方案设计

### 2.1 每页行数可配置（dbPageSize）

- 设置 → 数据库新增「每页行数」Select：10 / 50 / 100 / 500，默认 100（现状）；存 config.dbPageSize（进 configSyncKeys 白名单随设置同步）
- 读取：store._config.dbPageSize || 100（性能敏感路径读 _config 惯例），替换 PAGE_SIZE 常量两处使用（MySQL 翻页 + Redis SCAN）；服务端 1000 上限保持
- ⚠️ "默认 10"列为可选档位而非默认值：默认 10 的翻页次数 = 行数/10，大表操作成本过高；若坚持默认 10 改一个常量即可（1 行）

### 2.2 页内虚拟渲染（核心）

- DbGridTable 的 Table 增加 virtual 属性（跟随 scroll.y 一起启用：virtual = y > 0）
  - 已有 scroll={{ x: 'max-content', y }} 满足 virtual 前置条件
  - 行高需固定：size='small' + 单行省略（现状 ellipsis）→ 行高恒定，符合 RcVirtualTable 要求；长文本已被 ellipsis 截断不会破坏行高
- 适用范围：主数据网格 / SQL 结果 / Redis 键列表 / hash/list/set/zset 详情（全部走 DbGridTable，一处开关全局生效）
- 表结构 tab 行数少，同样开启无副作用（行数 < 可视行数时自动退化为全渲染）

### 2.3 Redis 大集合详情分批加载（可优化点 ③）

- hash/list/set/zset 详情：后端 cap 1000 保持，前端改「加载更多」模式——首屏渲染前 200 行，点击按钮再追加下一批（前端切片，不重复请求；仅当首批=1000 时才再发一次续拉）
- 触发条件：d.rows.length > 200 时显示按钮；避免多数小键多一次点击

### 2.4 明确不做

- 全表懒加载/滚动到尾自动翻页：与服务端分页语义冲突（排序/跳页/总行数估算都要重算），且隐藏翻页操作对审计型使用不友好——保持显式翻页
- 值预览 pre 行级虚拟：单文本节点无行概念，内存小，不做

## 四、七维度速评

| 维度 | 评 |
|---|---|
| 功能正确性 | ⚠️ virtual 与行双击编辑/排序/选中叠加需实测（行虚拟化后滚动定位行为变化）；pageSize 切换后页码重置为 1 |
| 主题兼容性 | ✅ N/A |
| 视觉一致性 | ⚠️ virtual 模式滚动条由 RcVirtualTable 接管，需确认与全局滚动条观感一致；行 hover/选中样式不变 |
| 无障碍 | ⚠️ 虚拟列表下屏幕阅读器只见可视行（antd virtual 既有行为，非本设计引入） |
| 性能 | ✅ DOM 行数与 pageSize 解耦；redis 大 hash 峰值从 ~50MB 降到 ~10MB |
| 可维护性 | ✅ 复用 DbGridTable 单点开关 |
| 可回滚性 | ✅ virtual 一处布尔 + pageSize 一处常量，独立 revert |

## 五、验证计划

1. CDP + 真实库：100 行页 → 断言 DOM 行数 ≈ 可视行数（~20）而非 100；翻页/排序/双击编辑/查找高亮不回归
2. redis：1000+ field 大 hash → 首屏 200 行 + 加载更多逐步追加；堆采样对比
3. pageSize 各档位切换 → 翻页正确、总行数估算不变
4. npm run test-unit-ci（858+ 契约更新）

## 六、决策点

| # | 问题 | 建议 |
|---|---|---|
| D1 | 默认每页行数 | 100（现状）；10 作为可选档——默认 10 在大表下翻页成本过高 |
| D2 | virtual 是否全表开启 | 是（行少自动退化，无额外成本） |
| D3 | redis 详情首批行数 | 200 + 加载更多 |
