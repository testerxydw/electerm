## 〇、结论摘要（先看这张表）

| 层次 | 是什么 | 统一可行性 | 判定依据（能否满足"同一业务概念 + 同一变化原因"） | 建议 |
| --- | --- | --- | --- | --- |
| **L1 骨架** | 高度、背景、底部分隔线、左右内边距、移动端形态、窗口级动作的位次 | **高**（应统一） | 所有页面顶栏都是"会话级工具条"，高度/视觉随设计规范整体变化 | ✅ 做（方案 A） |
| **L2 内容槽** | 左侧信息（连接信息 vs 引擎/目标/状态）、页面级开关（只读/刷新/keepalive/广播/换行…） | **低**（不统一） | 内容随业务走：终端跟 SSH/SFTP/串口特性变，数据库跟 db-client 变 → 概念与变化原因都不同 | ❌ 不做（保持各自渲染） |
| **L3 窗口级动作** | 查找、全屏（以及未来的复制、截图、固定…） | **高**（应统一） | 都是"窗口能力"，与业务无关，且总是因同一个原因（新增/调整窗口能力）一起变化 | ✅ 做（方案 A 核心） |
| **L4 查找引擎** | 匹配 + 高亮 + 定位 | **不能共用引擎**，只能共用 **UI + 计数 + 导航** | 终端是在 xterm 字符缓冲上搜索（有滚动条刻度、能滚动到命中）；数据库是在 DOM 文本上搜索 | ⚠️ 拆成 `SearchBar(UI)` + `provider(引擎)` |

**一句话**：**能统一的是"骨架 + 窗口级动作 + 查找 UI"，不能统一的是"页面内容"与"查找引擎"**。用户的三条直觉里——"搜索不用实现两个"**部分成立**（UI/计数/导航可共享，引擎必须各一个）；"顶栏功能修改不用同步两边"在**窗口级动作**上完全成立；"统一性更好"对**骨架/视觉**成立，对**内容**不成立（强统一会引入伪抽象）。

**推荐路径**：方案 A（共享骨架 + 共享窗口级动作组件 + 共享查找 UI，引擎按页面注入）→ 观察后再决定是否上 B（DB 状态上提、真一栏到底）；**不建议 C**（把 DB 塞进 `SessionControl`）。

> 📌 **v2 扩展**：§十一~§十四 把上述判定标准套到**其余所有页面**后，原方案 A 有一处重要修正——本仓库**已经存在**一个被 rdp/vnc/spice 三页共用的共享骨架 `RemoteSessionShell`，它正是 §6.2 想要的 flex 列形态；因此"新建骨架"应改为"**提升该既有组件为通用 `SessionShell`**"，且"只有 2 类页面需要顶栏"的前提被推翻（实为 6 类）。同时新发现 4 个"动作集合不共享"的活样本（telnet 整类动作缺失、web 缺全屏、全屏入口 2 份实现、查找 3 套 UI）。

### 1.4 查找：两套实现（事实澄清）

- 终端那个"搜索"按钮在数据库页**原本是空操作**：`session.jsx:511-513` 的 `handleOpenSearch` 走 `refs.get('term-' + tabId)?.toggleSearch()`，数据库页没有终端实例 → 静默 no-op（`?.` 吞掉）。所以"搜索不用实现两个"的前提要先修正为：**旧的不是"两个实现"，而是"一个实现 + 一个死的入口"**。
- 现在两套：终端 = 引擎级（xterm addon，能定位/滚动/带选项/带刻度）；数据库 = 页面级（DOM 标记 + 计数，无定位无选项）。

## 二、"统一"到底能统一什么 —— 逐层判定

> 判定标准采用项目既有的最小抽象原则：**共享抽象的所有调用方必须属于同一个业务概念、遵循同一协议/约束、预期因同一业务原因共同变化**。逐层套用：

### L1 骨架（高度/视觉/位次）—— 判定：**满足**
- 同一业务概念：都是"会话内容区顶部的工具条"。
- 同一变化原因：设计规范调整（高度从 32 → 34、加底部分隔线、图标统一为 18px、hover 色改为 `--hover-bg`）会**同时**影响所有页面。
- 现状反证：终端用裸 `<span className='sess-icon pointer'>`，数据库用 antd `Button type='text'` → 两处 hover/尺寸/焦点环不一样；终端有移动端分支，数据库没有。

### L2 内容槽（信息 + 页面级开关）—— 判定：**不满足**
- 终端的 keepalive/broadcast/wrap/分屏/SFTP 跟随/pane 切换属于 **SSH/SFTP/串口**业务；数据库的只读/刷新/引擎/库名属于 **db-client** 业务。
- 变化原因不同：上游改 SSH 特性不会动只读开关；db-client 增加"切换库"也不会动 keepalive。
- 且 §三 的收益测算是"窗口级动作"与"骨架"，与内容无关。→ 强行抽出"内容槽协议"（`items: []` 配置化）会造成"为了配置而配置"：每个字段都要经过一层声明式描述，调试与类型（实际是 JS）收益为负。

### L3 窗口级动作（查找、全屏）—— 判定：**满足（应共享）**
- 同一概念：窗口能力，与业务无关。
- 同一变化原因：新增"截图/固定标签/全屏"这类动作时，几乎总要在**所有会话页**同时出现。
- 现状证据：**遮蔽 `SessionControl` 时连丢"全屏"入口**（`f23f1949` 才补回）、"查找"入口在数据库页是空操作 → 正是"动作集合不共享"导致的两次功能缺失。

### L4 查找引擎 —— 判定：**不能共用，但可协议化**
- 终端：对 **xterm 字符缓冲**搜索，返回 `{resultIndex, resultCount, matchIndex}`，可 `findNext/findPrevious` 滚动到命中，`activeMatchColorOverviewRuler` 支持"概览刻度"。
- 数据库：对 **DOM 文本**搜索，命中即标记，计数天然来自 DOM；"滚动到第 N 个命中"需要 `scrollIntoView`，"概览刻度"没有对应物（可不要）。
- 二者差异会渗到 UI（刻度、`textarea` 里无法高亮）→ **共享 UI 层、引擎各自实现**是唯一不别扭的形态。

**判定汇总**：统一的目标应精确表述为 —— **"共享骨架 + 共享窗口级动作 + 共享查找 UI；内容与引擎各自实现"**，而不是"整个顶栏一个组件"。

## 三、收益（尽量用已经发生的事做证据）

1. **消灭"漏功能"这一类回归（最高价值）**
   - 已经发生：① 遮蔽 `SessionControl` → 丢"全屏"入口（`f23f1949` 修）；② 数据库页"查找"入口点了没反应（本次才修，`8bffcbe9`）。
   - 统一动作集合后，新增窗口级动作"改一处、所有会话页自动获得"，这类缺失在结构上不可能再出现。
2. **高度/布局口径单点化，消掉一类"幽灵留白"**
   - 现状：32px 这个数在 **5 处**表达（`constants.js:30`、`terminal.styl:14`、`sessions.jsx:37`、`session.jsx:241`（补偿）、`db-session.styl` 的 `.db-head`）。
   - 已经发生：数据库页底部 32px 留白（`4ab6164a` 修）——根因就是"JS 扣减"与"页面自渲染 bar"两套口径并存。
   - 统一为"bar 高度由 token 决定 + 内容区 `flex:1`"后，**两侧都不需要再做算术**。
3. **视觉/交互一致性**：hover 反馈、图标尺寸、tooltip 位置、移动端收纳形态一致；不再出现"两套 bar 各自演化"。
4. **查找行为一致（用户心智统一）**：终端已有完整模型（输入框 + `(i/n)` + 上一个/下一个 + 大小写/整词/正则 + Esc 关闭）。数据库当前只有子集（无定位、无选项）。共享 UI 后，可一次把"上下一个 + 当前命中区分色"带给数据库。
5. **测试/契约成本摊薄**：一个动作组件的行为（含无障碍、焦点环、快捷关闭）只需一套契约与单测；新增会话页只需"填内容"，不必重复实现并补测试。
6. **移动端不再漏**：共享骨架后，数据库页自动获得移动端收纳（现在数据库页在窄屏下是靠 flex 挤压，`.db-head` 里的搜索框 + 只读 + 刷新 + 全屏会挤掉信息文本）。

## 四、代价与风险（含对 §三 的反证）

1. **状态所有权冲突（最大难点）**
   - `SessionControl` 是**无状态展示组件**，所有业务状态在 `session.jsx`（class）里，通过 props/handler 下传；
   - 数据库的连接状态、只读开关、树刷新、查找词都在 `DbSession`（函数组件 + `manate auto` + `lazy()`）**内部 state**。
   - 要让"一个共享 bar"显示数据库内容，只有三条路：
     - (a) **DbSession 受控化**：把 `readOnly / connError / treeLoading` 与 `onToggleReadOnly / onReload / onSearch*` 全部上提到 `session.jsx`（"真统一"，但 DbSession 内部有 10+ 处状态与回调，且它是 lazy + auto 订阅 store 的形态，受控化会改变重渲染语义与时机）；
     - (b) **经 store/context 中转**：把"某 tab 的只读开关/查找词"放进全局 store → 污染全局状态、放大订阅面（改一次开关会触发订阅者重渲染），还要处理 tab 关闭清理；
     - (c) **分层**：只共享骨架与窗口级动作（这两者本来就无需上提状态），页面级内容留在页内（改动最小）。
   - **结论**：只有 (c) 的收益/风险比合理；(a) 才是"一栏到底"的完整统一，值得在有第三个会话页（或 DB 功能继续膨胀）时再评估。
2. **伪抽象风险（与项目规则直接冲突）**
   - 目前"需要顶栏"的只有 **2 类**页面（终端族 / 数据库）；rdp/vnc/web/telnet/ftp/spice **明确不要**顶栏（`session-control.jsx:59` 直接 return null）。
   - 为第 2 个使用点引入"顶栏框架 + 内容槽协议"，属于"第 2 个调用点就抽象"；若没有第 3 个消费方，这套协议没有任何一处会因它而受益，只增加间接层。
3. **上游合并成本：自渲染反而更省事（对 §三.6 的反证）**
   - `session-control.jsx` / `session.jsx` 是**上游改动最频繁**的文件之一；把数据库内容塞进去 → 每轮 `git merge -X ours` 都要在同一个文件里反复裁决。
   - 而 `.db-head` 在我们自己的 `db-session.jsx` 里 → 与上游**零冲突**。所以"统一"要选在"上游很少改、且是本项目共享基建"的文件里（如新建 `session-bar.jsx` / `search-bar.jsx`），**不要寄生到上游组件内部**。
4. **性能回归**：若走 (a) 受控化，切换只读/刷新都会触发 `session.jsx` 重渲染 → 整个 `SessionControl` + 视图子树重渲染；现在这些是页面局部 state 更新。需要额外 `memo`/`shouldComponentUpdate` 才能不退化。
5. **查找"统一"的语义陷阱**
   - 终端的匹配选项（大小写/整词/正则）与"滚动到命中"在 DOM 文本上要么不适用（正则/整词可做但语义会漂），要么需要额外实现（滚动定位、当前命中高亮）。
   - 若把 xterm 的 `SearchAddon` 语义硬套到 DOM，会出现"看起来一样的 UI，行为不一致"（例如 `n/m` 计数含义、`Enter` 行为、关闭是否清空关键字）。→ 共享 UI 时必须把"能力差异"显式表现为 **provider 能力位**（如 `canScrollToMatch`），而不是假装一样。
6. **回归面**
   - `SessionControl` 现役调用方：SSH、本地终端、串口（以及可能的 telnet/ftp 分支外的路径）。改它的 prop 契约会波及这些路径与移动端分支。
   - 抽共享组件时若不改契约（只把"查找/全屏"两个动作替换成共享组件），回归面最小化到"两处调用"。

## 五、方案对比

### 方案 Ø（现状）
- 终端 `SessionControl`、数据库 `.db-head` 两套；高度靠 JS 补偿对齐；查找两套。
- 优点：与上游零冲突；每页可自由演化。
- 缺点：动作集合漂移（已丢全屏/空操作搜索）、高度口径 5 处、视觉/移动端不一致。

### 方案 A（**推荐**）：共享骨架 + 共享窗口级动作 + 共享查找 UI（引擎分注入）

| # | 动作 | 落点（新建/修改） | 说明 |
| --- | --- | --- | --- |
| A1 | 抽 `SessionBarActions`（无状态）：渲染"查找 + 全屏"（可扩展） | 新建 `src/client/components/common/session-bar-actions.jsx` | props：`{ searchOpen, onToggleSearch, onFullscreen, disabled }`；终端与数据库各传自己的 handler（数据库传 `store.toggleSessFullscreen(true)`，终端传 `handleFullscreen`） |
| A2 | 骨架统一为 `SessionBar`（容器）：`height var(--bar-h)`、`border-bottom`、`padding`、`display flex` | 新建 `session-bar.styl`（或用既有 `.terminal-control` 抽出共用样式） | 终端 `SessionControl` 与数据库 `.db-head` 都套这个容器样式；**移动端收纳形态**也在此层决定 |
| A3 | 高度单点化 | 新增 token `--session-bar-h: 32px`（`css/includes/tokens.styl`），`termControlHeight` 从它派生或直接废弃 | 消除 5 处数值；`computeHeight` 保留（终端仍有 bar 占位），但数据库不再补偿（用容器语义而不是算术） |
| A4 | 查找 UI 抽 `SearchBar`（输入框 + `(i/n)` + 上一个/下一个 + 关闭 + Esc） | 新建 `src/client/components/common/search-bar.jsx` | 终端 `TermSearch` 改用它（选项按钮作为 slot）；数据库也用它，注入 DOM provider |
| A5 | 查找 engine 协议（最小）：`{ find(kw), next(), prev(), clear(), count }` | 不改终端引擎，只加轻包装；数据库实现 DOM 版 | 数据库可先只实现 `find/clear/count`，`canScroll` = false → UI 隐藏"上下一个" |
| A6 | 数据库查找补"当前命中区分色" | `db-session.styl` + `hlText` | 与终端"当前命中 vs 其他命中"两种颜色对齐 |

- 预计改动：新建 3 个小文件 + 2 处调用点 + token 1 个 + 数据库查找小改；**不动 `DbSession` 的状态所有权**。
- 收益：§三 的 1/2/3/4/5/6 全部拿到（内容层除外）。
- 风险：低（两处调用点、可逐步回滚）。
- 验证：CDP 实测（终端与数据库各自的查找/全屏行为、`(i/n)` 计数、移动端收纳）+ `npm run test-unit-ci`（CSS 契约/token）。

### 方案 B（中等）：A + 数据库内容槽上提
- 额外把 `.db-head` 左侧信息（引擎/目标/状态/重连）与只读/刷新移到共享 bar 的内容槽，`DbSession` 改为受控（props 提供状态 + 回调）或经 **context**（`DbSessionContext`）由 bar 消费。
- 收益：真正"一栏到底"，视觉完全一致；数据库页内部结构更清爽。
- 代价：`DbSession` 受控化改造（10+ 状态/回调）；重渲染面扩大；需要在 `session.jsx`（上游高频文件）里加 DB 分支 → 合并冲突面上升。
- 建议：**先在 A 上跑一段时间**；若数据库页功能继续膨胀（例：连接信息需要可点、切库、SQL 执行状态上栏），再评估 B，并优先用 context 而非 props 下钻。

### 方案 C（不建议）：把数据库内容并进 `SessionControl`
- 单个组件按 `tab.type` 分支渲染所有页面内容；调用方统一为一个。
- 缺点：单组件多职责；把 db 业务状态上提到上游组件；**上游高频文件冲突最大化**；移动端分支耦合；与项目"最小抽象"规则冲突（变化原因不同却强行同一实现）。
- 结论：不采用。

## 十、专项：数据库页的「字体与字号」是否与终端统一

> 用户问题：「数据库页面的字体和大小与终端统一？」

### 10.1 现状（证据）

| 维度 | 终端 | 数据库页 |
| --- | --- | --- |
| 字体族 | **用户可配**：`config.fontFamily`（默认 `Maple Mono, mono, courier-new, courier, monospace`），可被 tab 级 `tab.fontFamily` 覆盖 | UI 系统字体栈（`basic.styl:9`）+ 局部固定等宽 token `--font-mono`（`tokens.styl:66`，与终端配置**无关**） |
| 字号 | **用户可配**：`config.fontSize`（默认 **16**，`default-setting.js:12`），tab 级可覆盖；设置页可改（`setting-terminal.jsx:518`）；Ctrl± 走 `term.zoom()`（**运行时缩放，不落配置**，`session.jsx:526-533`） | 全局 12px（`basic.styl:7`），局部显式 12px（`.db-tree-db-count`、`.db-grid-total`、`.db-value-pre`、`.db-conn-fail-raw`） |
| 应用点 | xterm canvas（`term-init.js:31,37`） | 已用等宽的三处：`.db-value-pre`（值预览）、`.db-sql-editor`（SQL 编辑器）、`.db-conn-fail-raw`（原始错误）；**网格单元格、树里的对象名仍走 UI 字体** |
| 其它页面先例 | — | 无：全仓库除终端外没有页面跟随终端字体（`sftp/code-compare.jsx:114` 是硬编码 13px） |

### 10.2 收益（为什么值得统一）

1. **数据面可读性/对齐**：数据库网格、键列表、SQL、JSON 都是"代码/标识符"，等宽 + 数字对齐（`tabular-nums` 在等宽下天然成立）显著优于变量宽字体；列宽不再因数字位数跳动。
2. **用户已调好的字体复用**：用户已经把终端字体挑成"看得清、支持中文"的那一款（含 CJK 回落偏好）；数据库页不必再让他们在别处重复配置。
3. **与终端并排时视觉一致**：同屏上下分屏（终端 + 数据库）时，两处字号差异（16 vs 12）目前非常明显；统一后读感连续。
4. **与"顶栏统一"同一逻辑**：都属于"显示页统一"的用户可感知部分，成本远低于重构状态所有权。

### 10.3 代价与风险（必须写清）

1. **16px vs 12px 基线冲突（最大）**：DB 页现在是 12px 设计（antd `size='small'` 表格、32px 顶栏、紧凑行距）。若**字号整页跟随** `config.fontSize`（默认 16），会出现：表格行高被撑高、单页可见行数骤减、顶栏文本裁切、`ellipsis` 触发变化。要跟字号就必须**同时**把行高/单元格 padding/顶栏字号绑定到同一变量，并按字号给出行高公式。
2. **用户可能把终端字号调得很大或很小**（例如 20 或 10）：数据库页只有在"绑定变量 + 合理 clamp（如 11–18）+ 行高联动"时才不崩。
3. **CJK 混排列宽跳动**：等宽英文字体的中文是**逐字回落**（浏览器按字符回落），中英混排时"等宽"只对拉丁字符成立 → 中文列边距不齐。这是等宽的固有代价（终端里由 xterm 统一单元格宽度规避，DOM 里做不到完全一致）。
4. **Nerd Font / 连字**：终端字体可能含图标私用区与连字（Maple Mono 有连字）。DOM 里连字默认按 `font-variant-ligatures` 规则生效，若数据里出现 `->`/`!=` 等会被连字合并（终端 canvas 行为不同）→ 需显式 `font-variant-ligatures: none` 或接受差异。
5. **xterm 的字号语义 ≠ DOM**：xterm `fontSize` 是 canvas 逻辑 px（含 devicePixelRatio 处理与 cell 度量），DOM 是布局 px → 视觉接近但不保证逐像素一致，不能拿"看起来一样"当验收标准，只能按"读感接近"验收。
6. **Ctrl± 缩放不跟随**：`term.zoom()` 是运行时瞬态（不落配置），DB 页若读 `config.fontSize` 则**不会**跟着放大缩小 → 需要在文档/UI 说明，或者干脆用一个独立配置项而不是隐式跟随（避免用户困惑"我在终端里放大了，数据库没变"）。
7. **不应统一的部位**：顶栏文字、Tabs、按钮、tooltip、错误文案（自然语言）→ 若也换等宽大字，会破坏 UI 层次并撞上 antd 度量（这部分属于 §二 的 L2，判定仍是"不统一"）。

### 10.4 三个范围与推荐

| 方案 | 内容 | 改动 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| **1** | **只统一"字体族"**：数据面（网格单元格、键列表、SQL 编辑器、值预览、原始错误）用 `config.fontFamily`（+ 兜底栈），字号保持 12px | 1 个注入点（在 `DbSession` 根部 style 写 CSS 变量）+ 网格加 `font-family`/`font-variant-numeric`；把 `--font-mono` 的三处换成语义变量 | 低 | ✅ **先做** |
| **2** | **字体族 + 字号**都跟随终端，作为**独立配置项**（如 `dbFontFollowTerminal`，默认关；开启后 `--db-code-size: clamp(11px, config.fontSize, 18px)` 且行高/单元格 padding 联动） | 配置键 + 设置页开关 + 行高联动 | 中（需实测行高/裁切/大字号） | ⏳ 视需要再做 |
| **3** | **整页**（含标签/按钮/树文字）跟随终端字体与字号 | 全局变量 + antd 组件度量覆盖 | 高 | ❌ 不建议 |

**推荐路径**：先落 **方案 1**（纯视觉收益、风险低、与"关键字高亮/查找高亮"等已有数据面能力同层），观察使用后再决定是否加**方案 2** 的开关。

### 10.5 若做方案 1：落点清单

| # | 落点 | 内容 |
| --- | --- | --- |
| 1 | `db-session.jsx` 根部 | `style={{ '--db-code-font': `${tab.fontFamily \|\| config.fontFamily}, ${--font-mono 兜底栈}` }}`（tab 级覆盖与终端口径一致：`tab.fontFamily \|\| config.fontFamily`） |
| 2 | `db-session.styl` | `.db-grid-table`（单元格/表头）加 `font-family var(--db-code-font)`；`--font-mono` 的三处改用它；统一 `font-variant-ligatures none`（避免连字，见 10.3.4） |

| 4 | 顶栏/Tabs/按钮/tooltip | **不动**（保持 UI 字体） |

### 10.6 决策点

| ssh 的文件管理面板（同屏子页） | 同 ftp：**面板级** title + AddressBar（左右分屏各一套） | 同上 | `computeHeight` | KeywordFilter | 无 | 同上 |
| 无会话（空状态） | `no-session.jsx` | — | — | — | — | — |

**一眼结论**：顶层"条"有 **5 种互不兼容的实现**（`SessionControl` / `.db-head` / `RemoteSessionShell` 控制条 / web `AddressBar` / sftp title+AddressBar）；高度口径有 **4 种**（JS 扣减 / JS 扣减+补偿 / CSS padding 抵消 / 两条叠放自适应）；"查找"有 **3 套语义不同的实现**；"全屏入口"有 **2 份实现 + 2 类页面整体缺失**；"移动端收纳"有 **3 种策略**。

## 11.2 最重要的发现：`RemoteSessionShell` 已经是 §6.2 想要的形态

- 它是**本项目自有文件**（不在上游高频文件里，天然满足 §七 D2），被 rdp/vnc/spice **三个页面**共用 → 是"共享骨架"在全仓库**唯一的既有正例**，同时直接推翻 §四.2 的前提（"需要顶栏的只有 2 类页面"→ 实际 6 类）。
- 它的结构恰好就是 §6.2 建议的 flex 列：控制条 `flex 0 0 auto` + 视口 `flex 1 1 auto; min-height 0`，且视口尺寸用 **ResizeObserver 实测**而不是从 props 推导（注释明确说明 fullscreen 下 props 会失效，`remote-session-shell.jsx:1-17`）——这正是终端 `.term-wrap`（`position:absolute` + JS 算尺寸，`session.jsx:343-376`、`terminal.styl:21-26`）应当学习的一面。
- 它的 `controlLeft / controlRight / floatControl / overlay` 是 **ReactNode 插槽**，不是声明式 `items: []` 协议 → 证明"共享骨架"**完全不必**引入 §四.1/§四.2 担心的伪抽象：**插槽式组合 ≠ 数据协议**，插槽只是组合，不产生"为了配置而配置"的间接层。
- 待收敛点：① 高度不固定（与两条 32px 的 bar 视觉节奏不一致）；② 移动端是 flex-wrap 换行，与终端 Popover 收纳两套心智；③ 全屏图标由 `session.jsx` 以 props 函数注入（`fullscreenIcon`），而 `session-control.jsx:288` 与 `db-session.jsx:1240` 又各自实现了一份 → **同一个"全屏"动作在全仓库有 2 份实现**（rdp/vnc/spice 复用同一份，是唯一做对的地方）。

**对原方案 A 的修正**：不必"新建 `session-bar.jsx`"，应**把 `RemoteSessionShell` 提升为通用 `SessionShell`**，让终端 / 数据库 / web / ftp 都套这个容器；窗口级动作收敛为 A1 的 `SessionBarActions`，由 shell 的 `controlRight` 插槽渲染。这样连"第 2 个调用点就抽象"的指控也不成立——**改造第 1 天就有 6 个调用方**。

## 11.3 telnet：一个「完整终端 + 零窗口级动作」的活样本

`isNotTerminalType` 把 telnet 归入"非终端"（`session.jsx:386-397`）只是为了关掉 `SessionControl`，但 `renderTerminals` 并未为 telnet 准备替代渲染 → telnet 落到 Term 分支（`session.jsx:343-383`），拿到一个**完整可用的终端**，却**没有查找、没有全屏、没有字体缩放、没有触摸端上下文菜单、没有换行切换**。

这是比 §三.1 两条旧证据更硬的一条：**动作集合不共享 → 新页面类型被整类动作遗漏**。方案 A 落地后，telnet 只需"接入 shell + 填内容"，窗口级动作自动获得。顺带：`isNotTerminalType` 这个名字与实际语义（"这条 bar 不适用于该类型"）已经脱节，重构时应改名（如 `hideSessionControl`）以免再次误导。

## 11.4 web：第 5 套条 + 整类窗口级动作缺失

- `.web-address-bar` 无任何专属 CSS（仅 `pd1`），高度随 antd 默认 Input 尺寸漂移；地址栏可被 `tab.hideAddressBar` 整条隐藏 → 唯一一个"用户能把顶层条变没"的页面。
- 没有查找、没有全屏 → 与 §三.1 同源的第三、第四个样本。
- webview 内查找技术上不可行（Electron 未对 `<webview>` 暴露页内查找 API）→ 属 L4 判定的"引擎不适用"。正确处理是 **UI 上显式不提供**（让用户知道"这里没有查找"），或退化为"在默认浏览器打开"（已有 `GlobalOutlined`，`web/address-bar.jsx:60`）；而不是像现在这样连入口都没有、用户无从推断。

## 11.5 ftp / sftp 文件管理面板：两条叠放的条 + 第三种查找

- 一个 ftp / ssh-fileManager 会话的顶层实际是**两行**：`sftp-panel-title`（`remote: user@host` + reload，或 `local`）+ `AddressBar`（路径输入 + 隐藏文件 / 上级 / 主页 / 关键字过滤 / 书签 / 前往）。两行高度都自适应、都无 token。
- 分屏时它是**面板级**条（左右各一套 title + address）→ 说明"条"当前同时跨"会话级"和"面板级"两个层级，这正是 L1 应当区分、而现状混在一起的原因。
- 查找第三种实现：`KeywordFilter`（`sftp/keyword-filter.jsx`）是"过滤列表"语义，与终端"高亮+计数+定位"、数据库"高亮+计数"都不同 → 印证 §1.4 的修正：**全仓库"搜索"是三套语义 + 三套 UI，不是两套**。
- 自带 `MobileAddressPrefix` Popover → 第三种移动端收纳策略。

## 11.6 数据库页内部还有 3 条「页内条」

`.db-grid-head`（表名 + 行数 + 翻页 + 刷新）、`.db-redis-bar`、`.db-redis-detail-bar`（`db-session.styl:180,315,342`）都是"面板工具条"。它们与顶层 bar 不是同一概念（属 L2 内容），但**骨架规则相同**（高度 / 间距 / hover / 图标尺寸）→ 建议 A2 的骨架样式同时以 `PanelBar` 形态供它们使用，避免第 4、第 5 种"条"继续增生。

## 11.7 非会话页面：边界判定（不建议纳入）

底栏（`.main-footer` 30px，`footer.styl:1-3`）、设置面板、快速命令面板（`qm.styl:39-43`）、侧栏、传输面板、AI 对话、空状态页——它们的"条"变化原因是"全局工具 / 设置"，与会话页不同（不满足 L1 的"同一变化原因"）。**不建议**纳入 `SessionShell`；但建议它们复用同一批 **token**（高度 / 间距 / hover 色 / 图标尺寸）——这是 §6.2 token 单点化的附带收益。

# 十二、统一矩阵：所有页面 × 所有层次

| 页面 | L1 骨架 | L2 内容 | L3 窗口级动作 | L4 查找引擎 |
| --- | --- | --- | --- | --- |
| 终端族 | 统一（32px） | 各自渲染 | **统一**（查找 / 全屏 / 字号 / 上下文菜单） | xterm addon（可滚动 + 概览刻度） |
| 数据库 | **统一**（高度 token） | 各自渲染 | **统一**（查找 / 全屏） | DOM 标记 + 计数（可补 next/prev） |
| rdp / vnc / spice | **统一**（高度 token，保留 wrap 能力） | 各自渲染（传输就绪 / 刷新 / 缩放） | **统一**（全屏；`RemoteFloatControl` 保留为"远程专用浮层"） | 不适用（canvas）→ UI 不提供 |
| web | **统一**（高度 token / 可隐藏） | 各自渲染（地址栏） | **统一**（补全屏；查找显式不提供） | 不适用（webview） |
| telnet | **统一**（接入 shell） | 无（终端内容即全部） | **统一**（当前 0 个 → 自动获得） | xterm addon（复用终端 provider） |
| ftp / 文件管理 | **统一**（`PanelBar` 收敛两行） | 各自渲染 | **统一**（补全屏；查找走过滤语义 → 独立 provider） | 列表过滤（语义不同，能力位 `canFilter`） |

> 矩阵读法：**L1 / L3 两列全绿才动手；L2 全列保持各自渲染；L4 按引擎分 provider、UI 共享**。这与 §二 的判定标准完全一致，只是适用范围从 2 类页面扩展到 6 类。
