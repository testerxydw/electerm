### 1. 现状调研结论

#### 1.1 连接类型体系
- 书签（bookmarks 表）按 `type` 字段区分连接类型，已支持：ssh / telnet / serial / local / ftp / web / rdp / vnc / spice
- 类型常量集中在 [src/client/common/constants.js](file:///media/dp25/DATA/deb/fcitx5-deb/github/electerm/src/client/common/constants.js#L149-L157)
- 书签树（bookmarkGroups）、书签表单（bookmark-form 组件群）、快速连接（quick-connect 协议串）、deep-link 均以 type 为分发键

#### 1.2 数据层
- 统一 API：`dbAction(dbName, op, ...args)`，双引擎（node<22 用 @electerm/nedb，node>=22 用内置 node:sqlite），见 [db.js](file:///media/dp25/DATA/deb/fcitx5-deb/github/electerm/src/app/lib/db.js#L11-L16)
- 16 张表，bookmarks 表已在加密白名单（safe-storage 静态加密），见 [nedb.js](file:///media/dp25/DATA/deb/fcitx5-deb/github/electerm/src/app/lib/nedb.js#L11)
- 存储位置：`DATA_PATH || appPath/electerm/users/defaultUserName/`

#### 1.3 可复用基建
| 基建 | 位置 | 复用点 |
|---|---|---|
| 书签表单 | src/client/components/bookmark-form/ | 新增数据库连接表单区块 |
| 书签分组树 | bookmarkGroups 表 + 左侧栏 | 数据库连接挂入书签树 |
| 密码加密 | safeEncrypt/safeDecrypt（safe-storage） | 数据库密码静态加密，随 bookmarks 表 |
| SSH 基建 | ssh2（已有依赖） | 数据库 SSH 隧道 |
| 连接测试 IPC 模式 | src/app/lib/ipc.js | 新增 testDbConnection handler |

**结论：数据库连接应以"新书签类型"融入现有书签体系，而非另起一套连接管理。** 可免费获得分组树、搜索、复制、同步（sync 体系）等既有能力。

### 3. 阶段1 详细设计

#### 3.1 数据模型（复用 bookmarks 表，推荐）

新增 type 为 `database` 的书签文档，扩展字段（仅 database 类型使用）：

```
type: 'database'
dbType: 'mysql' | 'redis'                     // 引擎，MVP 两种
dbHost: string                                // 数据库主机
dbPort: number                                // 默认 mysql 3306 / redis 6379
dbUser: string                                // redis 可空
dbPassword: string                            // 随 bookmarks 表整体加密
dbName: string                                // 默认库（redis 可空）
sshTunnelBookmarkId: string                   // 绑定已有 SSH 书签作隧道（可空=直连）
```

否决方案：新建 dbConnections 独立表 —— 需复制一套分组/表单/树/同步逻辑，重复面大，不推荐。

#### 3.2 数据库类型范围（MVP）

| 类型 | 驱动 | 体积 | 阶段 |
|---|---|---|---|
| MySQL | mysql2 | ~2MB | MVP（用户点名） |
| Redis | ioredis | ~1MB | MVP（用户点名） |
| PostgreSQL | pg | ~1.5MB | 二期 |
| MongoDB | mongodb | ~10MB | 二期评估（体积大） |

驱动在主进程**懒加载**（首次连接测试才 require），不增加启动耗时；包体积约 +3MB。

#### 3.3 改动点清单

新增文件（为主，与上游冲突面小）：
1. `src/app/lib/db-client/index.js` — 客户端工厂：`getDbClient(dbType)` 懒加载驱动，统一接口 `testConnection(opts)`
2. `src/app/lib/db-client/mysql.js` / `redis.js` — 各引擎实现（阶段1 仅 testConnection，为阶段2 预留 query 接口位）
3. `src/app/lib/db-tunnel.js` — SSH 隧道：复用现有 ssh2 连接基建（forwardOut 建本地随机端口 → dbHost:dbPort）

修改文件（少量，各 1-2 处）：
1. [constants.js](file:///media/dp25/DATA/deb/fcitx5-deb/github/electerm/src/client/common/constants.js) — 新增 `dbTypeMap`、`terminalDatabaseType = 'database'`
2. [src/app/lib/ipc.js](file:///media/dp25/DATA/deb/fcitx5-deb/github/electerm/src/app/lib/ipc.js) — 新增 `testDbConnection` IPC handler（组装隧道+驱动，返回测试结果）
3. bookmark-form（render-form.jsx 等）— 按 `type === 'database'` 条件渲染数据库连接区块：引擎选择、host/port/user/password/database、SSH 隧道绑定下拉（列已有 SSH 书签）、「测试连接」按钮
4. 书签树图标映射 — database 类型专属图标
5. 双击书签行为 — database 类型阶段1 仅执行连接测试并 toast 结果；阶段2 打开数据库浏览器 tab

#### 3.4 交互流程（阶段1）

1. 左侧栏书签树 → 新建书签 → 类型选「数据库」→ 选引擎（MySQL/Redis）→ 填连接参数
2. 可选绑定 SSH 隧道：下拉选择已有 SSH 书签（复用其 host/port/user/key）
3. 「测试连接」：隧道(若有) → 驱动 connect → 成功/失败 toast（失败带错误摘要）
4. 保存 → 出现在书签树（支持既有分组/搜索/复制/删除）
5. 双击 → 阶段1 执行测试连接并提示；阶段2 打开数据库浏览器

#### 3.5 安全要点
- dbPassword 随 bookmarks 表走 safe-storage 静态加密（现有链路，零新增）
- SSH 隧道凭据不复制，运行时引用所绑 SSH 书签
- 日志脱敏：连接串打日志时隐藏密码

#### 4.2 页签内布局（db-session.jsx，lazy 加载）
```
┌────────────┬──────────────────────────────────┐
│ 元数据树    │  Tabs: [数据] [SQL查询] [表结构]    │
│ (antd Tree)│  数据:   antd Table 分页网格       │
│ 库 → 表/视图│  SQL:   编辑器 + 执行按钮 + 结果网格│
│ 工具条:刷新 │  结构:   列定义表格                │
└────────────┴──────────────────────────────────┘
```
- 树：库 → 表/视图（懒加载展开），点击表 → 右侧打开该表数据 tab
- 网格：antd Table，服务端分页（LIMIT/OFFSET），列排序（ORDER BY），MVP 只读展示
- SQL 编辑器：MVP = textarea + Ctrl/Cmd+Enter 执行 + 结果网格（多语句多结果集 tab）；CodeMirror6 语法高亮列二期
- Redis 特化：树=db0~db15 → SCAN 分页键列表；详情按 string/hash/list/set/zset 类型化展示 + TTL 显示；MVP 键详情只读 + 删除/改 TTL

#### 4.3 主进程扩展（src/app/lib/db-client/）
统一接口（各引擎适配器实现）：
```
getMetadata()        // 库列表/表/视图（树数据）
getPageData({table, page, pageSize, orderBy, order}) // 分页数据
describeTable(table) // 列结构
executeSql(sql)      // SQL 执行（返回 {fields, rows, affected}）
close()              // tab 关闭时断开
```
- index.js 从 `testDbConnection` 扩为 `getDbClient(dbBookmark, sshBookmark)` 工厂：建连接（含隧道，复用 db-tunnel）并返回带上述方法的实例；连接实例缓存按 tab.id 管理
- 生命周期：tab 打开 → 懒建连接；tab 关闭（delTab 钩子）/ app 退出 → close 断开，防连接泄漏
- 保活：mysql2 enableKeepAlive；ioredis keepAlive 由 TCP 层
- 断线：操作报错时 UI 顶栏显示断开提示 + 重连按钮（重建 client）

#### 4.4 IPC 与安全
- 渲染层经 `window.pre.runGlobalAsync('dbClientOp', { tabId, op, args })` 调用（复用 trusted-sender 的 asyncGlobals 通道，无需新增 ws 通道）
- 只读防护（决策点 D1）：可选只读模式（连接配置开关，默认开）——主进程对 executeSql 做白名单校验（仅 SELECT/SHOW/DESC/EXPLAIN）；Redis 只读命令白名单（GET/HGETALL/LRANGE/SMEMBERS/ZRANGE/SCAN/TTL/TYPE）
- 大表防护：网格强制分页，单页上限 1000 行；无主键表提示只读

### 一、现状核实（先澄清一个前提）

| 项 | 现状 | 结论 |
|---|---|---|
| 表数据加载 | MySQL 走服务端分页 LIMIT/OFFSET（mysql.js:171-183），Redis 走 SCAN 游标（redis.js:151） | **"剩下的数据不加载"已经成立**——任何时刻只取当前页（≤100 行），不会整表进内存 |
| 每页行数 | PAGE_SIZE = 100（db-session.jsx:21），写死 | 可优化点 ① |
| 页内渲染 | antd Table 把当前页 100 行全部渲染成 DOM（每行含高亮 span 树/编辑态） | 可优化点 ②（真正内存点） |
| Redis 大 hash/list 详情 | hgetall/lrange 一次取上限 1000 行全量渲染 | 可优化点 ③（redis 侧最大内存点） |
| antd 能力 | 6.5.1 的 Table 支持 virtual 属性（InternalTable.js:423 → RcVirtualTable，需配合 scroll.y——DbGridTable 已传 y） | 页内虚拟渲染的现成抓手 |

#### 内存收益的诚实评估

renderer 私有总量 142MB 中，表格 100 行 DOM 约占 2~5MB（每行单元格含 React 节点/高亮 span）。把每页 100→10 条的直接内存收益只有 1~4MB，占比很小；真正的价值排序：

1. **页内虚拟渲染（virtual）**：DOM 行数与 pageSize 解耦——pageSize 100/500 时 DOM 始终只有可视区 ~20 行，内存低 + 长列表滚动流畅，收益最大且不牺牲翻页体验
2. **Redis 大 hash 详情 1000 行**：一次 hgetall 的 1000 行 DOM 才是 redis 侧真正的内存点（估计 20~50MB），改分批加载收益实在
3. **每页行数可配置**：交互 vs 内存的权衡交给用户，默认值不建议激进到 10（100 万行的表要翻 10 万次页）

### 二、方案设计

#### 2.1 每页行数可配置（dbPageSize）

- 设置 → 数据库新增「每页行数」Select：10 / 50 / 100 / 500，默认 100（现状）；存 config.dbPageSize（进 configSyncKeys 白名单随设置同步）
- 读取：store._config.dbPageSize || 100（性能敏感路径读 _config 惯例），替换 PAGE_SIZE 常量两处使用（MySQL 翻页 + Redis SCAN）；服务端 1000 上限保持
- ⚠️ "默认 10"列为可选档位而非默认值：默认 10 的翻页次数 = 行数/10，大表操作成本过高；若坚持默认 10 改一个常量即可（1 行）

#### 2.2 页内虚拟渲染（核心）

- DbGridTable 的 Table 增加 virtual 属性（跟随 scroll.y 一起启用：virtual = y > 0）
  - 已有 scroll={{ x: 'max-content', y }} 满足 virtual 前置条件
  - 行高需固定：size='small' + 单行省略（现状 ellipsis）→ 行高恒定，符合 RcVirtualTable 要求；长文本已被 ellipsis 截断不会破坏行高
- 适用范围：主数据网格 / SQL 结果 / Redis 键列表 / hash/list/set/zset 详情（全部走 DbGridTable，一处开关全局生效）
- 表结构 tab 行数少，同样开启无副作用（行数 < 可视行数时自动退化为全渲染）

#### 2.3 Redis 大集合详情分批加载（可优化点 ③）

- hash/list/set/zset 详情：后端 cap 1000 保持，前端改「加载更多」模式——首屏渲染前 200 行，点击按钮再追加下一批（前端切片，不重复请求；仅当首批=1000 时才再发一次续拉）
- 触发条件：d.rows.length > 200 时显示按钮；避免多数小键多一次点击

#### 2.4 明确不做

- 全表懒加载/滚动到尾自动翻页：与服务端分页语义冲突（排序/跳页/总行数估算都要重算），且隐藏翻页操作对审计型使用不友好——保持显式翻页
- 值预览 pre 行级虚拟：单文本节点无行概念，内存小，不做

### 一、现状与问题

#### 1.1 结构（`db-session.jsx:1089` + `db-session.styl`）

```

  └─ db-redis-area (flex 列, gap 8)

#### 1.2 问题

| # | 问题 | 证据 |
|---|---|---|
| 1 | 键列表 `max-height 45%` 是**固定上限**，与内容无关 → 视觉上"上下平分"；键少时上带小、键多时永远卡在 45%，大键库无法把更多空间给列表 | 真实库 db0=6 键：列表 186px；db1=21 键也顶多 45% |

| 3 | 比例不可调：不同键库规模差异极大（6 键 vs 1 万键），固定比例无法适配 | — |

#### 1.3 约束（易踩坑，设计必须满足）

1. **DbGridTable 定高滚动**：键列表与详情网格的 scroll.y 依赖 wrap 拿到确定高度——任何新分配必须保证两个 wrap `flex 1 1 0 + min-height 0`（或等价的确定高度）；给 auto 高度 + 内部 basis 0 会整块塌陷（Redis 键列表塌陷事故已发生过一次）。
2. **tab 布局的影响**：
   - Redis 右侧**当前没有** Tabs 包裹（MySQL 的 data/SQL/表结构才有 `.db-tabs`），高度链是 `db-main-panel → db-redis-area` 直通，比 MySQL 少一层 antd Tabs pane；
   - 若未来把键列表/详情**套进 Tabs**（如仿 MySQL 加「键空间 / 控制台」tab）：antd Tabs pane 是**块级父级**，内部 flex-basis 不生效，必须 `height 100%` 撑满（表结构 tab 踩过），且 `.db-tabs` 的 body-holder→body→content 撑满链已现成可复用；
   - 本设计**不引入 Tabs**（见方案对比），上述只是高度链备查。
3. 详情 bar（键名/TTL/删除）必须始终 `flex none`，不能被压缩。

### 三、推荐实现（方案 A）

#### 3.1 结构与样式

```

  ├─ keys wrap (.db-redis-keys)      flex 1 1 0 + min-height 0   ← 去掉 max-height 45%

- `.db-redis-resizer`：**复用 `.db-tree-resizer` 的既有模式**（骑跨分隔线的 1px 线 + hover 高亮 `--primary`），方向改 `row-resize`；定位算术参照树分隔条的 margin 负值方案（横向改为纵向：`margin: -12px 0` 骑跨上容器下边框……具体以树分隔条实现为准的镜像）。

#### 3.2 拖拽逻辑（照抄树宽拖拽的模式）

- `redisSplitPct` state（默认 50），`onMouseDown` 记起点 → `mousemove` 按容器高度换算百分比（clamp 20%~80%）→ 松手 `localStorage.setItem('electerm-db-redis-split', pct)`（键名与 `TREE_WIDTH_KEY` 同风格，进 constants）；

- 初始化读 localStorage，非法值回落 50。

#### 3.3 未选键态

- 详情区不存在时（`!redisKey`）渲染 `<Empty description='select a key' />` 占位（居中于下半区）——平分后有内容支撑，不再大片空白；
- Empty 外仍包一层 `flex 1 1 0 + min-height 0 + 居中` 容器，保证选键后网格拿到的仍是同一确定高度（切换不抖动）。

## 6. 数据库表格横向滚动条优化方案

> 原文档：`数据库表格横向滚动条优化方案-2026-10-15.md`（2026-10-15）

> **状态：✅ 已完成（2026-10-21 复核）**：DbGridTable 统一横滚条已落地，真实库+真机验证通过（`1d01a4b0`）。

### 一、问题

数据表（数据 tab 的表格页）行数超过可视区时，横向滚动条位于**全部行之下**，必须先纵向滚到最底部才能看到并拖动它。

根因：`.db-grid-table`（antd Table，`scroll={{ x: 'max-content' }}`）所在容器是唯一滚动容器（`flex 1; overflow auto`，`db-session.styl:218`），横向滚动条由这个"整页高"的容器产生，天然沉在内容最底部。

### 二、候选方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 纯 CSS 把滚动视口移进 antd 内层 `.ant-table-content` | 给 antd 内部 wrapper 链（5 层 div）逐层设 `height/max-height 100% + min-height 0` | 不改 JSX | 依赖 antd 6 内部 DOM 结构，升级易碎；antd 官方未承诺该层级稳定 | 弃 |
| B. `scroll={{ x: 'max-content', y: <数值> }}` | antd 官方用法：表头与 body 分离渲染，body 自己定高滚动 → 横向滚动条**固定在可视区底边，永远可见** | 官方能力、代码量小；顺带获得**表头吸顶**（滚行时列名不消失） | `y` 需数字，需测量容器高度（ResizeObserver） | **采用** |
| C. 自绘悬浮滚动条（overlay 同步原生滚动） | 在容器底边画一条假滚动条 | 不依赖 antd | 同步逻辑复杂、拖拽/键盘/惯性全要自己处理 | 弃（仅当 B 失效再议） |

### 三、推荐实现（方案 B，最小改动）

> **2026-10-15 更新**：按用户要求已统一处理所有会横向溢出的网格——抽为本文件内组件 `DbGridTable`（`db-session.jsx`），主数据网格 / SQL 结果 / 表结构 / Redis 详情（hash/list/set/zset）/ Redis 键列表 7 处全部换用；配套 CSS：`.db-grid-table-wrap`（scroll 容器）、`.db-sql-result` 内 antd Spin 包装层参与 flex 传高、`.db-struct-area` 用 `height 100%` 撑满 tabpane（块级父级里 flex-basis 不生效）。真实库（192.168.115.67:13306 tgfsom.tgfsom_operation_log，24 万行）实测：data/SQL/表结构三处横滚条均常驻可视区底边（偏差 0px）、表头吸顶；Redis 页共用同一组件与布局模式（本机无 redis 服务未实测，待用户环境复测）。

原设计范围（初版仅主网格）：

#### 改动点

1. `db-session.jsx`（dataArea）：
   - Table 外包一层 `<div className='db-grid-table-wrap' ref={wrapRef}>`，接管原 `.db-grid-table` 的 `flex 1 1 0; min-height 0`。
   - 新增一个**组件内局部**的容器高度测量（`useRef` + `useEffect` + `ResizeObserver`，直接写在 `db-session.jsx` 内，不新建文件——当前只有一处调用，不满足抽 hook 的条件）：
     ```jsx
     const gridWrapRef = React.useRef(null)
     const [gridWrapH, setGridWrapH] = React.useState(0)
     const [gridHeadH, setGridHeadH] = React.useState(0)
     // 容器高度：ResizeObserver 观察 wrap；表头高度：MutationObserver/轮询一次读取 .ant-table-thead
     // y = gridWrapH - gridHeadH，二者任一 <=0 时不传 y（保持现状）
     ```
   - Table 改为 `scroll={{ x: 'max-content', ...(gridWrapH > gridHeadH && gridHeadH > 0 ? { y: gridWrapH - gridHeadH } : {}) }}`。
   - ⚠️ hook 必须写在 `db-session.jsx` 既有的 `if (error) return` / `if (!ready) return` **之前**（hook 顺序契约，此前已踩过崩页坑）。
2. `db-session.styl`：
   - 新增 `.db-grid-table-wrap { flex 1 1 0; min-height 0; display flex; flex-direction column }`。
   - `.db-grid-table` 去掉 `flex 1 1 0; min-height 0; overflow auto`（滚动权移交 antd 内部 body），仅保留类名挂载。
   - 颜色/圆角不涉及，无 CSS 契约新增风险；如新增 token 需过 `css-tokens.spec.js`。

#### 行为效果

- 行多 + 列宽（如截图 1 的 `tlp_hbon_hook_task`）：横向滚动条常驻可视区底边；表头吸顶，纵向滚动时列名恒可见。
- 行少（截图 2 `tlpbon_operation_log` 一屏内）：无变化。

#### 边界与风险

| 点 | 处理 |
|---|---|
| 首帧 height=0 | `y` 不传，保持现状渲染；ResizeObserver 回调后再 setState 补上（一次闪动可接受） |
| 窗口/分屏/树宽拖拽导致容器变化 | ResizeObserver 天然覆盖 |
| antd `scroll.y` 模式下列宽 | `scroll.x='max-content'` 已存在，header/body 分离下 antd 用同一 colgroup 对齐，不受影响 |
| 错误 Alert/分页条占位 | 它们在 wrap 之外（`.db-grid-area` 内、wrap 之前），wrap 实测高度自动扣除，无需手算 |
| 屏幕阅读器/键盘 | 原生滚动容器不变（只是从外层移到 antd body 层），无回归 |
