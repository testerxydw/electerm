## 0. 结论先说

**护栏做得好，生态没打通，体感差一口气。**

1. **最大缺口是 MCP client 缺位。** electerm 的 MCP 能力只有 server 侧（45 个工具对外暴露），全仓没有任何 MCP client 实现——AI agent 的工具集被焊死在 38 个内置工具上，接不进外部 MCP 生态（数据库 CLI、浏览器、工单系统……）。竞品终端（Warp、ChatWise 类）已把"AI + 任意 MCP server"当标配。这是拉开代差的一项。
2. **体感瓶颈是 agent 非流式。** agent 循环每轮 `AIchatWithTools` 非流式整段等待（`agent.js:136`），一轮工具调用可能沉默十几秒，用户只看到转圈。ask 模式有流式，agent 反而没有——恰恰是 agent 最需要。
3. **安全有 2 个实打实的洞**：AI 配置（含 apiKey）明文存本地 db 且不进 sync 加密名单；MCP 鉴权接受 `?apiKey=` 查询参数且代码里主动生成带 apiKey 的 URL（会落访问日志/剪贴板）。
4. **易用性欠的是小件**：无重试/重新生成、无面板快捷键、无 /命令、来源上下文只提示不绑定。都是小改动，但都是高频挫败点。

不建议动的：DB AI 护栏链（生成只写编辑器不执行 + `db-sql-risk.js` 六级分类 + 边界块防注入）设计扎实，是本项目 AI 侧最值得保持的优势，任何优化都不得绕开它（AGENTS.md §5.2.6）。

## 2. 优化点矩阵

优先级判据：P0 = 安全洞 / 生态代差；P1 = 明显体感与能力缺口；P2 = 打磨项。

### P0（安全与生态）

| # | 类别 | 问题（事实） | 建议 | 主要涉及 |
|---|---|---|---|---|
| 1 | MCP | 全仓无 MCP client，agent 工具封死在 38 个 | 新增 `mcp/client/`：用户可配置外部 MCP server（stdio + Streamable HTTP 两种传输），tools/list 动态注册为 agent 工具，走现有 tool-call 卡片与 zod 子集校验；敏感工具复用 mcp-transfer-guard 人工确认 | 新目录 + `agent.js` + `agent-tools.js` 动态化 + `ai-config.jsx`（MCP server 列表 UI） |
| 2 | 安全 | AI 配置明文存储；sync 不加密 | apiKey 过系统凭据管理（Electron safeStorage）；sync 加密名单补 aiConfig | `sync.js:96`、AI 配置存取层 |

## 4. 风险与不做清单

- **不做**：AI 自动执行 SQL/命令的任何旁路（现有"只写编辑器 + 用户确认 + danger check"是硬边界，见 `agent.js:29-51` 系统提示词声明）。
- **不做**：替换自研 zod 子集为官方 zod（体积 vs 收益，现有 208 行覆盖 tools 入参校验够用；若 #1 client 需要更全的 schema 校验再评估）。
- **风险**：#1 MCP client 引入外部工具 = 引入第三方提示词注入面——工具结果必须过与 `db-sql-ai.js:37-60` 同口径的边界块消毒，且默认不自动执行任何写操作工具，写操作一律人工确认。
- **风险**：#4 agent 流式改造涉及三协议 tool_call 分片聚合，是本轮最大工程量；建议在 #1 之前单独成批（与 2026-10-31 批次"分三层落地"同套路）。
