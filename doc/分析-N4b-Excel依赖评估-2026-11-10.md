# 分析-N4b-Excel依赖评估-2026-11-10

> 结论先行：**推荐 `node-xlsx@0.25.0`** 作为 N4b Excel 导入/导出的统一引擎（零依赖、内嵌 SheetJS 0.20.3 已修全部已知 CVE、unpacked 2.7MB、Apache-2.0、维护活跃）。npm 源的 `xlsx` 包因高危无修复**排除**；`exceljs` 因体积/依赖/维护放缓**不推荐**。
>
> 本文档只做依赖评估，不含任何代码改动（TODO 主文档 §N4 "评估依赖体积与许可证后再定" 的答卷）。

## 1. 候选库对比

| 库 | 版本 | 许可证 | unpacked | 运行时依赖 | 最近发版 | 已知 CVE | 判定 |
|---|---|---|---|---|---|---|---|
| **node-xlsx** | 0.25.0 | Apache-2.0（附 LICENSE-SheetJS） | 2.7MB | **0**（内嵌 SheetJS 0.20.3） | **2026-11-09** | 内嵌版本已修（见 §2） | ✅ 推荐 |

## 2. CVE 核实（实测 npm audit + 官方 advisory）

- `xlsx@0.18.5`（npm 能装到的最后一版）实测 `npm audit`：
  - **GHSA-4r6h-8v6p-xvw6 / CVE-2023-30533 原型污染（high 7.8）**：影响 < 0.19.3，修复版只发 cdn.sheetjs.com；
  - **GHSA-5pgg-2g8v-p4x9 ReDoS**：修复在 0.20.2；
  - npm 上 "No fix available" → 引入即带高危，除非改用自建 CDN tarball 源（供应链口径变化，不推荐）。
- `node-xlsx@0.25.0` 解包实测：内嵌 `XLSX.version = "0.20.3"`（`dist/src-D8tETrLD.cjs`），含 `safe_parse_wb` 补丁 → **两个 CVE 均已覆盖**（0.20.3 > 0.20.2 > 0.19.3）。
- 注意点：内嵌意味着 npm audit **不会**自动标记内嵌 SheetJS 的未来 advisory，需手动跟踪上游 CHANGELOG（升级动作 = 升 node-xlsx，一行）。

## 3. 实测基准（本机 Node 22，50k 行 × 10 列，含数字/布尔/日期/中文/NULL）

| 操作 | node-xlsx (SheetJS 0.20.3) | exceljs (stream) |
|---|---|---|
| 写出 | 2.0s，文件 6.7M（`writeOptions.compression:true`），ΔRSS ~274M | 1.0s，文件 2.9M，ΔRSS ~210M |
| 导入解析 | 1.9s，ΔRSS ~228M，**全内存** | 流式 1.2s，ΔRSS ~239M |
| 类型还原 | **开箱即用**：number→number、boolean→boolean、日期→`YYYY-MM-DD` 字符串（可 `cellDates`） | 默认全 string，需按 `cell.type` 手工折算 |
| 空单元格 | 中间 null 保留；**尾部 null 被吞**（`[null,2,null]` → `[null,2]`） | 同样尾部缺失，且 `row.values` **1-indexed 稀疏数组**，错位风险更高 |

- SheetJS 默认写出未压缩（同数据 17.2M），**必须传 `compression:true`**（node-xlsx 透传 `writeOptions`，实测有效）。
- xlsx 格式层面**尾随空单元格不落盘**：两家解析器行为一致，不是库缺陷 → 导入端必须按表头长度 pad（实现要点，见 §4）。

## 4. 未来 N4b 动手时的实现要点（评估阶段预案）

1. **导入通道**：xlsx 是 zip 二进制，不适配 `db-import/parsers.js` 的 `createState/feed(chunk)/finish` 文本流契约 → 注册表加独立分支：整文件解析（新增 `MAX_XLSX_BYTES` 大小护栏，风格对齐 `MAX_SCRIPT_BYTES=8MB` 的既有口径，建议 32MB）→ rows 直接进 mapping/insert-batch 分批管线，取消/进度/任务表全部复用。
2. **尾列 NULL 补齐**：解析后按首行表头长度 pad 缺失尾部单元格 → NULL（所有 xlsx 库共性，必做，否则最后一列为 NULL 时会缺列错位）。
3. **预览**：用 `parseMetadata()`（实测返回 sheet 名单 + `{s,e}` 范围含行数）免整表解析 → UI 加 sheet 选择；执行时才 parse 选中 sheet。
4. **导出**：`db-exporter.FORMATS` 加 `'xlsx'`；页循环累积 array-of-arrays，结束时一次 `build(..., {writeOptions:{compression:true}})`。内存随总行数线性（50k 行 ~270M 峰值）→ 建议沿用导出既有取消机制并设行数上限提示（超大表引导用 CSV）。
5. **类型口径**：SheetJS 还原 JS 原生类型，与 CSV 导入的"全字符串"口径不同 → mapping 层明确声明（数字/布尔直通，日期保持 `YYYY-MM-DD` 字符串），避免隐式类型漂移。
6. **二进制信封列**：`__bin` 未截断信封在 xlsx 里写标记文本而非 base64（base64 会膨胀 33% 且 Excel 无意义），与 sql 侧 `X'hex'` 的显式标记思路一致。
7. **打包瘦身**：实装 2.6M（`dist/index.cjs` 4K 入口 + 1.3M cjs 实现 + 1.3M mjs 实现）；主进程只用 CJS → `prune-node-modules.js` 清单可删 `dist/*.mjs`/`*.d.ts`/`bin/`（省 ~1.4M），新增依赖需进 prune 保留名单核查。

## 5. 为什么不是 exceljs / read+write-excel-file

- **exceljs**：唯一支持真流式读写的候选，但为它付出 21.8MB + 9 个运行时依赖（含带 moderate 漏洞的 uuid，升级到 11.x 是 breaking）+ 一年未发版，且空单元格稀疏数组/1-indexed 的错位坑反而更费防御代码。数据库工具的典型规模（几万~几十万行）SheetJS 全内存路径实测可承受。
- **read-excel-file + write-excel-file**：MIT、活跃、轻，但要两把依赖且 API 窄（写侧无共享字符串优化、读侧类型推断弱）；`parseMetadata` 式预览需自己实现。作为 node-xlsx 不可用时的备选。
