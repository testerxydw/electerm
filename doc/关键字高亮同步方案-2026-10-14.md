## 3. 前提与范围（重要）

1. **无历史同步数据**：`keywords` 从未被上传过，云端没有这个字段 → 加入同步不需要迁移、不会覆盖本地。
2. **参与同步的设备都使用含分组模型的版本**（本次改动之后发布的包）。因此不需要为"老客户端不认 `source/group/off`"设计兼容层。
   - 唯一残留注意事项（不是设计约束，写在这里备查）：老版本客户端的 keywords 表单只提交 `keyword/color`，若在**未升级**的设备上编辑并保存，会丢掉 `group/off`。只要不混用旧包，这条不会发生。
3. **语义选择**：`setConfig` 是整键覆盖，所以"是否合并"是个**产品选择**（多设备冲突时谁赢），不是兼容要求。

## 4. 备选方案（已按"无兼容负担"重排）

### 方案 A —— 直接把 `keywords` 加入同步白名单（最小改动，推荐起步）

- **做法**：`configSyncKeys` 增加 `'keywords'`。整数组（含 `source/group/off`）随 `userConfig.json` 上传；下载时按现有逻辑整键覆盖。
- **优点**：改动约 1 行；语义与其它所有设置项一致（"以最后一次上传为准"）；不需要合并逻辑与迁移。
- **缺点**：多设备同时改规则时会互相覆盖（B 设备下载后即变成 A 设备的规则）——这与字体、主题等其它同步项的行为完全相同。
- **影响面**：`src/client/store/sync.js`（白名单）。
- **验证**：改一处规则 → 上传 → 另一设备下载 → 分组/勾选/静音状态一致；云端 `userConfig.json` 里能看到 `keywords` 与 `source/group/off` 字段。

### 方案 B —— 白名单 + 下载时按规则合并（多设备体验更好）

- **做法**：在 A 的基础上，下载后不整组替换，而是按 `keyword` 文本合并：
  - 本地保留自己的 `group/off`（静音状态不被远端翻动）；
  - 云端有的规则补进本地，云端没有的本地规则保留；
  - 颜色冲突以云端为准（或弹提示，二选一）。
- **优点**：多设备各自维护静音/分组互不打架。
- **缺点**：要写合并逻辑 + 单测；与其它配置项的"覆盖"语义不一致，需要说清规则。
- **影响面**：`sync.js`（下载分支）、`keyword-groups.js`（新增 `mergeKeywords(local, remote)`）、单测。
- 备注：B 可以在 A 之上叠加，**不推翻数据模型**，所以"先 A 后 B"是低风险路径。

### 方案 C —— 分组/静音元数据搬到独立 config 键（不推荐）

- **做法**：`config.keywords` 只存"生效中的规则"，`keywordGroups` 单独存分组与静音映射。
- **原本的价值**是兼容不认新字段的老客户端；在本方案的 §3.2 前提下，这个价值不成立。
- **剩余价值**：如果将来要做"按分组整体启停、且希望老包也能安全共存"，再考虑。当前改动量最大（模型 + 迁移 + UI 取值），**不推荐**。

## 5. 推荐

- **第一步：方案 A**（1 行改动，语义与其它同步项统一，验证成本最低）。
- **第二步（可选）：升级到方案 B**，如果实际使用中出现"多设备互相覆盖"的困扰。
- 方案 C 暂不考虑。

## 6. 顺带可做的小改动（与同步无关）

给面板的「导入」增加选项 **「保留原分组与静音状态」**：当前导入一律归入「用户」分组并丢弃 `off`，用它当"跨设备搬运"手段时会丢信息。有了方案 A 之后这条只是备选。
