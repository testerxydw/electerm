# 设计：数据库页「查找」与「过滤」的分工（MySQL/Redis 浏览页搜索形态）

> 状态：设计稿（暂不实施）· 日期：2026-10-19
> 问题：MySQL/Redis 浏览页应该单独做搜索框，还是复用顶栏查找？
> 关联：`doc/TODO-顶栏与显示页统一执行计划.md` S3/S4（顶栏统一查找条已落地）、`doc/草图-统一搜索条.html`

---

## 一、结论

**不新增浏览页级"搜索框"；复用顶栏查找 + 各面板保留/增强"过滤"入口。**

核心判据：**查找（find）和过滤（filter）是两个语义**，物理载体不同，不该合并也不该互相替代：

| | 查找（顶栏） | 过滤（面板） |
| --- | --- | --- |
| 回答的问题 | "这段文本在页面哪里" | "我只看满足条件的数据" |
| 作用对象 | DOM 可见内容（树/网格/键列表/详情） | 数据源（SCAN MATCH / WHERE） |
| 引擎 | DOM 扫描 + `<mark>`/选区 | 服务端命令或客户端行筛 |
| 是否滚动定位 | 是（scrollIntoView / 选中） | 否（结果集本身变小） |

## 三、为什么不建议浏览页再做独立搜索框

1. **语义冲突**：同一页出现两个"搜索框"，用户无法区分"这个和顶栏那个有何不同"。保持「顶栏=查找、面板工具条=过滤」的固定分工，心智负担最低。
2. **虚拟渲染的硬边界**：网格 virtual 渲染每页只挂 ~18 行 DOM（页大小 20），顶栏查找天然只能找"看得见的行"。想在**全量数据**里找值，本质是数据查询，只能走过滤（行筛/WHERE），顶栏查找在物理上替代不了——这恰好证明两者必须分层。
3. **抽象协议保护**：`common/search-bar` 是"纯 UI 查找条"（引擎注入 find/prev/next）。若下放做数据过滤，就得加服务端查询、防抖重查、清空回位等语义，破坏其单一协议，违反最小抽象原则。
4. **已有先例**：Redis 键面板的 filter 就是"面板级过滤"的正确形态——它长在数据源旁边、绑定 SCAN MATCH，而不是模仿一个通用搜索框。

## 四、可选增强（按价值/成本排序，均未实施）

### A · 顶栏查找支持 textarea「选中定位」（低成本，建议做）✅ 2026-10-19 已实施
- 计数：扫 textarea 的 `value`（`indexOf` 全量），命中并入 `(i/n)`；
- 导航：命中列表 = `<mark>` 数组 + textarea 文本偏移；轮到 textarea 命中 → `focus()` + `setSelectionRange(start, end)`，浏览器自动滚入可视区；
- 妥协（唯一）：textarea 内其余命中无法提前标色，轮到时才可见。
- 范围：仅 `db-session.jsx` 计数/导航逻辑，不动 SearchBar 协议。

### B · MySQL 网格头「当前页行过滤」（中成本，视需求）
- 位置：`db-grid-head` 页大小 Select 旁加一个小输入框（与 Redis filter 同视觉语言）；
- 行为：纯 client 过滤当前页 `dataSource`（防抖 150ms），清空还原；显示 `n/m rows`；
- 明确不做全表搜索——跨页找值属数据查询，二期再议 WHERE 下沉（需过只读白名单，注意 `EXPLAIN DELETE` 类误拦的已知限制）。

### C · WHERE 下沉服务端（二期，单独立项）
- 仅当"跨 24 万行找值"成为真实高频场景再做；涉及分页/排序联动与安全审查。

### 不做
- MySQL/Redis 浏览页各自独立的通用搜索框（理由见 §三）。

---

## 五、一句话

**顶栏查找管"看见的"，面板过滤管"要看的"**：Redis 已有 filter、MySQL 缺行筛（B）、textarea 定位可补（A）；浏览页不再新增第三种搜索入口。
