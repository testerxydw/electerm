# 关键字高亮：色板复用与密度治理 · 设计 v2（2026-11-05）

状态：**v2 定稿，未开工**。v1（`设计-关键字高亮色板与密度-2026-11-05.md`）保留不动，本文是全量替换版：收录 v1 的实测基线、WindTerm 实测、两条拍板与批次排期，并按用户 2026-11-05 的追加前提「**不严格对齐 WindTerm，按设计自己精简**」做了 11 处修订（见 §11 对照表）。

用户三条原始指令不变：① 共享规则抽单独分组，组与组之间不得有重复规则（共享的也不行）；② 100 多条太多，精简；③ 参考 WindTerm 默认高亮规则，其他规则尽量精简。

**前提变化**：WindTerm 从"目标形态"降级为"参照物"。它证明了"结构信号只给一档一色"能压住密度，但**一档一色只是它的手段**——染色面积由命中跨度决定，把青色和紫色规则合并成一条只改变色相分布，面积一点没降，还白丢一档区分度。所以 v2 不再复刻它的"9 类 / 约 30 条 / 一档一色"形状，判据只剩两条：**面积**（§7 密度闸）和**条数**（§6 按档分账的上限）。

## 1. 实测基线（本文所有判据的来源）

探针：把 `keyword-presets.js` 全量启用 → `activeKeywords` 去重 → 复刻 `highlight-addon.js` 的"合并大正则定位 + 同起点锚定取最短"裁决，对 13 类代表性输出逐条统计。脚本口径可复现（本轮为一次性探针，落地时固化成 `self-test/keyword-density-*`，见 §9）。

| 事实 | 数 |
| --- | --- |
| 预设组 / 组内条目 / 去重后生效 | 13 组 / **152 条** / **105 条** |
| 被多组重复引用的共享规则 | **19 条**；`ipv4` 一条出现在 **9 个组** |
| 全选用后对 15 行真实日志的染色面积 | **44%**（608/1396 字符） |
| 染色面积按色分布 | blue 47.9% · cyan 38.0% · green 5.1% · red 3.5% · magenta 3.1% · yellow 2.5% |
| 单行最惨 | **93%**（一行日志文件路径被 `absPath` 整条吃掉） |
| 面积大户 Top6 | `srcFile`(蓝) > `ts`(青) > `absPath`(蓝) > `URL`(蓝) > `ipv4`(青) > `num`(青) |
| 命中面最广 | `num` 13/13 类输出、`lvlError` 8 类、`ts` 6 类、`ipv4` 5 类 |

**结论一（满屏蓝的成因）**：不是色不够，是**每行必中的"结构类"信号占了 86% 的染色面积，且它们全挤在 blue/cyan 两色**；语义信号（红=错误、黄=警告、绿=成功）合计不到 12%，被淹没。→ 治理重点是**面积**，不是色相个数；这也正是"能不能多加几种色"（§8）不该排在密度治理前面的原因。

**结论二（面板口径失真）**：152 条目 vs 105 生效，"已应用 N/M"与实机着色对不上，根源是共享规则被按组重复写入——正是用户要消灭的那件事。

⚠️ 探针里"32 条在我这批语料 0 命中"**不能当死规则**：样例是手写的，没覆盖 git diff hunk、TLS 指纹、SQLSTATE、UUID 等形状。它只能当"命中面窄"的参考，删除判据见 §6。

**数字口径纪律（v2 新增）**：探针的 152/105 与 `keyword-groups.js:37` 注释里写的"136 条 → 102 条"已经对不上——这类具体数字散落在注释里必然过期。落地时**注释与文档都不写死条数**，条数一律由 spec 断言现算（§6.4）。

## 2. WindTerm 基准（实测，不是二手转述；v2 只作参照）

来源：`WindTerm_2.7.0_Linux_Portable_x86_64.zip` → `WindTerm_2.7.0/terminal/schemes/linux/linux.lexer`（7244 字节，291 行；仓库是发布壳，规则文件只在二进制包里，源码仓库无）。

| 维度 | WindTerm 默认 Linux | electerm 全选现状 |
| --- | --- | --- |
| 顶层语义类 | **9**（keyword / datetime / ip / mac / number / option / path / permissions / operator + string） | 13 组 |
| match/begin 模式条数 | **约 30** | **105**（条目 152） |
| "词档"条数 | **4**（error / success / warn / info，各一条大 alternation） | 20+ |
| 结构信号用色 | **`markup.heading` 一档一色吃下 datetime + IP + IPv6 + MAC** | 拆成 `ts`/`tsBracket`/`ipv4`/`ipv6`/`mac` 5 条、cyan+magenta 两色 |
| 层次手段 | grammar 上下文：prompt 行内才认 command/option、字符串整体一档、权限位逐字符四色 | 只有"整条匹配配一种颜色"，无行级上下文 |

**结论三（v2 修订）**：WindTerm 的克制来自**结构信号默认不进视野**——它的 lexer 只在被认作输出的上下文里跑，且靠 grammar 分层。我们没有上下文，就必须用别的机制把结构信号压住，那个机制是 §7 的档位与覆盖率闸，**不是把青色紫色合并成一档**。同色同类的合并照做（那是真冗余），异色的合并全部取消。

**搬不动的三档**（`keyword-presets.js` 文件头已声明，本文维持该口径）：prompt 行内的 command/option 分色、引号字符串整体染色、权限位逐字符四色——本引擎给整条匹配配一种颜色且无行级上下文，硬搬只会更难看。

## 3. 两处拍板（按建议执行）

1. **通用组拆三档**，不做一条整组：`通用 · 级别与状态`（signal）/ `通用 · 时间与数值`（structure）/ `通用 · 地址与路径`（structure）。
   理由：满屏蓝的主力恰是后两档；合成一条整组的话，"只想要错误词"的人必须连时间戳、裸数字一起吞下，密度问题原样保留。拆三档后，勾选粒度 = 密度粒度 = 改色粒度。
2. **老配置自动归并**：把命中共享集合的条目改写为 `group='通用 · …'`，同正则的重复条目折叠成一条。
   **v2 修订：折叠时不再判"用户是否改过色"**。面板对预设条目只读（`keywords-form.jsx:288` 的 `editable={!isPreset}`，色卡入口只在可编辑分支渲染），导入的条目一律 `source=user`——所以 `source=preset` 且色 ≠ 默认色这个状态**当前走 UI 走不到**，只有手改配置文件才出现。为一个不存在的状态写保色分支，等于给迁移引入一条无法覆盖的路径。判据挪到"角色改色"（§8）落地之后：那时用户真的能改一档的色，归并才需要保色。本轮迁移就是**纯归并 + 纯折叠**，幂等、可断言。

## 4. 批次 0（新增，前置）：两端重叠裁决同源

**v2 最大的一处精简，且是 §7 覆盖率闸的前置**。现状：终端"同起点取更短"（`highlight-addon.js:130`），网格"同起点取更长"（`db-highlight.jsx:68`），两端各扫各的（网格仍是每条正则各扫一遍整段文本，`db-highlight.jsx:45`，吃不到终端的单遍优化）。

为了让两端在同一行给出同一个结论，`keyword-presets.js` 里堆了一批**只为对齐而存在的让位护栏**：

| 位置 | 护栏 | 为什么存在 |
| --- | --- | --- |
| `keyword-presets.js:61` | `ipv4` 末尾 `(?!:\d)` | 把 `IP:端口` 整段让给端口映射档，否则终端染 7 字符、网格染整段 |
| `keyword-presets.js:73` | `ts` 的 `(?!\.\d)` | 不让时钟档抢 PCI 地址 `00:02.0` 的小数尾巴 |
| `keyword-presets.js:122` | `lvlError` 里 `DOES NOT(?: (?:EXIST\|MATCH))?` | 让红档自己吃下整句，避免终端取短只染两个词 |
| `keyword-presets.js:197` | `num` 的 `(?<!status[=:]\s{0,2})` | 把状态码起点整段让给 HTTP 的四色档 |
| `keyword-presets.js:477` | Docker 镜像名的 `(?![\w.-])` | 不与 systemd 的 `nginx.service` 抢出"紫 nginx + 蓝 .service" |

**做法**：把 `highlight-addon.js` 的 `buildScan` / `_collectMatches` / 起点裁决抽到 `src/client/common/keyword-scan.js`，终端与网格都调它；重叠口径**只保留一种**（沿用终端的"同起点取更短"，因为全部预设的排列顺序就是按"短的先赢"设计的，改成取长会让一批已固化的用例翻色）。

**收益（都是可减法的）**：
- 网格侧白拿 O(规则数 × 文本长) → O(文本长)，DB 大结果集单元格扫描不再随条数线性膨胀。
- 上表 5 处让位护栏连同注释可以删——裁决同源后，同起点谁赢不再取决于两端口径差，只需要规则自身顺序确定。
- 一致性从"两套实现恰好对齐"变成"同一套实现"：`highlight-equivalence.spec.js`、`db-highlight-length.spec.js`、`keyword-presets.spec.js:261` 那条"同一行在终端与数据库网格拿到的着色跨度一致"的双口径对比断言（终端 `a.end-b.end` vs 网格 `b.end-a.end`）退化为"两端调用同一函数"的等价断言，维护成本归零。
- §7 的覆盖率闸天然两端同实现，"两处必须一起改，否则又出现终端与网格结论不一样"这条约束从设计里消失。

## 5. 分组改造：跨组唯一 + 组依赖

- 新增 §3.1 的三个通用组，业务组不再抄共享规则；`keyword-presets.js` 文件头纪律 1 由"引用同一个共享对象"升级为"**一条正则在全部预设里只出现一次**"。
- **不变量升级**（`keyword-presets.spec.js:58` 的 "every preset is well formed"）：现在只查"组内不重复 + 同正则同色"，改为跨组唯一。这条一断，152/105 的错位从结构上不可能再发生。
- `mergeKeywordPreset` 的按正则去重降级为**兜底**（注释同步改口径：正常路径下不该再命中它）；`activeKeywords` 的按"正则+颜色"去重保留，它仍要服务"用户自定义规则撞预设正则"这种合法场景。
- 新增迁移函数 `regroupSharedRules(list)`（放 `keyword-groups.js`，纯函数、可单测）：按 §3.2 归并老配置，幂等。
- **v2 新增：组依赖 `requires`，补回被 §4/§5 拆掉的自足性**。跨组唯一之后，只勾 Networking 就没有 IP、只勾 HTTP 就没有时间戳——现在每个业务组自带 `rule.ipv4` 之类（如 `keyword-presets.js:320`），改造后这条体验会退化。做法：preset 定义上加 `requires: ['通用 · 地址与路径', …]`，勾选业务组时连带点亮被依赖的通用档；规则仍然全仓只存一份（满足用户"共享的也不行"），面板上组仍然自足。
  取消勾选要**按依赖计数**：一个通用档可能同时被 3 个业务组依赖，取消其中一个时若仍有已启用组依赖它，该档保持 on。

## 6. 精简：按档分账的上限

判据按优先级，不用"我这批语料没命中"当理由：

1. **只合并"同色 + 同类"的真冗余**（沿用文件头纪律 3，不同色绝不合并）：`ts` + `tsBracket`（青）合 1；`srcFile` + `absPath`（蓝）合 1；`dur` + `durKey`（青）合 1；`ipv6` + `mac`（紫）合 1。
   **v2 取消 v1 的三处异色合并**：`ipv4`(青) 不并进 `ipv6/mac`(紫)、`srcLoc`(紫) 不并进 `path`(蓝)、`hex`(紫) 不并进 `num`(青)。异色合并只改变色相分布、不减面积，还让 §9 的"blue+cyan 占比"判据自我矛盾（把紫色并进青色只会推高该比值）。
   Networking 的 `%FACILITY-N-` 三条 syslog severity 仍压成 1 条红档（6-7 档随通用 info/debug，这是"同档内砍低价值档"，不是异色合并）；HTTP 的 `[core:error]/[warn]/[info]` 三条与通用级别档重叠 → 删；Git 的 `diff --git` / `+++ ---` / `index` / `@@` 四条按色折成 2 条（蓝的 diff-header、紫的 index，`@@` 青随原序）。
2. **删低信噪比档**：`wordNote`（ACCESS/AUTH/PASSWORD 这类词几乎不带信息量，还要一大段否定式 lookahead 才不抢红档）、`permStr`（WindTerm 逐字符四色，我们整串一色反而更难看，文件注释自己承认只是"看得出来"）、`devAddr` 出通用档（改归内核组独有）。
3. **业务组只留"通用装不下的"**：领域词表与领域名词（接口名、pod 名、unit 名、SQL 关键词、镜像引用）留在本组；能并进通用档的一律先并。
4. **硬上限按档计，不按组计**（替换 v1 的"每组 ≤4 / 总数 ≤40"）：
   - v1 的"每组 ≤4"与它自己的目标形态表自相矛盾（同文档里 `通用 · 级别与状态` 就写了 6 条），而且会误伤天然多色的档——HTTP 的状态码按类分色本身就要占 4 条（`keyword-presets.js:378`），Git 的红/绿/黄/青四态也要 4 条，上限一压就只剩砍领域特性一条路。真正起约束作用的从来是总数（11 业务组 × 4 = 44 早已超过 40）。
   - v2 上限：`structure` 档全仓 **≤28** 条且默认不勾选；`signal` 档全仓 **≤32** 条；两者相加 → 生效总数 **≤60**（105 的近一半）。单组 >8 条时在预设表注释里写明"为什么不能并进通用档、为什么不能同色合并"。以后加一条得先减一条。
   - 面板条目数 = 生效数（§5 跨组唯一自动保证），这也是用户"100 多条太多"的第一层答案：152 这个数字本身就会掉到 60 以下。

目标形态（草案，条数以跨组唯一后的实际生效数为准，由 spec 现算）：

| 组 | 条数 | 档 | 内容 |
| --- | --- | --- | --- |
| 通用 · 级别与状态 | 7 | signal | lvlError / lvlWarn / lvlInfo / lvlDebug / wordOk / exc / nullBool |
| 通用 · 时间与数值 | 6 | structure | ts(含方括号) / dur(含 key=value) / size / num / hex / optFlag |
| 通用 · 地址与路径 | 5 | structure | ipv4 / addr6(ipv6+mac 同紫) / path(absPath+srcFile 同蓝) / srcLoc / url |
| Networking / Syslog / Kernel / HTTP / AppLog / Stack / Docker / Build / Git / Auth / Database | 合计 ≤42，单组 >8 需书面理由 | 两组混合 | 只留领域独有词表与状态档；领域名词类标 structure，默认关 |

## 7. 密度控制（砍条数不等于砍密度）

1. 规则加 `tier: 'signal' | 'structure'`（缺省按 signal 处理，老配置零迁移）。
2. **"全部应用"语义改为 signal 全开 + structure 按需**：现在 `setAll(true)`（`keywords-form.jsx:434`）把 105 条全上，等于强制打开最吵的结构档。改后全选 = 结构档默认关，面板上单独给"结构档"开关。工具栏按钮文案/tooltip 要写明"应用语义档"，否则用户按了老按钮发现比原来少染色会以为坏了。
3. **单行覆盖率上限**：一行染色占比 > 阈值（默认 35%）时该行只保留 signal 命中——直接消灭 93% 那种整行花屏。
   **v2 修订落点**：覆盖率必须**按行算**，而终端现在的处理单位是"写入片段"——`highlightKeywords` 对整个 text segment 一次裁决（`highlight-addon.js:235`），只有整次写入 > 4096 字符才按 `\n` 拆（`highlight-addon.js:277`）。attach 合并写入会把多行日志并成一个片段，按片段算占比 ≠ 按行算 35%（一行很脏、其余很干净 → 平均后不触发，阈值被静默放宽）。做法：裁决出 `filtered` 之后、拼 ANSI 之前，按 `\n` 把命中分组，逐行算占比再决定是否丢弃该行的 structure 命中。网格侧一个单元格即"一行"，同口径复用批次 0 抽出的同源扫描。
4. **结构档限跨度：本轮不做**（从 v1 的四道闸里摘出来）。覆盖率闸已经吃掉"一条胖路径吃满整行"这种主症状；限跨度只在"长行里孤零零一条 96 字符路径"这种边角有意义。批次 3 实机复测后如果该形状还在，再单独提。

## 8. 色板：角色改色先做，hex 后置

**v2 拆成两步，且把 hex 整块推到密度达标之后。**

- **本批做**：`keywords-form.jsx:57` 的 7 色 `Select` 换成 `components/common/color-card.jsx` 的形态（外面套 `bookmark-form/common/color-picker.jsx` 的 swatch + Popover），但**改色入口挂在 档/组 上，一次改一档**（v1 已判定：预设条只读，逐条点 40 次不是方案）。这条不引入新色域，只解决"改得动"。
- **后置（下一批再评估）**：`color` 允许 `#rrggbb` + `keyword-compile.js:27` 双分支真彩色 + 网格 `style.color` 分支 + 主题对比度门槛。理由：§1 结论一说的是**面积**问题，改色卡不减面积，做完 P3 还是满屏蓝；而它的成本是一整套——色码双分支、真彩色注入、按主题背景算对比度的门槛（色卡 24 色是为"徽标底色 + 运行时按 isDark 现算字色"挑的，`rand-hex-color.js:13`，前景色场景选 `#24292e`/`#ffd33d` 直接看不见）、深浅主题各一轮实机、还要动 `keyword-presets.spec.js` 里"颜色必须是 7 个 ANSI 名"的断言。性价比最低的一块排在最前面不值。
- **真要扩档位的判据**：终端主题本身有 16 个色名（`theme-defaults.js:86` 起 `black`…`brightWhite`），天然跟主题、零新代码。但**不保证 16 色可辨**：默认深色主题里 `brightRed` 与 `red` 同为 `#FF2C6D`、`brightGreen` 与 `green` 同为 `#19f9d8`（`theme-defaults.js:87`）。"7 色不够分"不是结论，"主题给的档位是否真的可辨"才是判据——批次 3 的实机数据出来再决定要不要真彩色。

与 §6/§7 的关系：**档与覆盖率闸解决"别糊屏"，角色改色解决"改得动"，色域扩展解决"能区分"**。前两个不做，第三个只把满屏蓝换成满屏紫。

## 10. 不做的事

- 不引入 grammar/行级上下文引擎去复刻 WindTerm 的 prompt 档与字符串档——成本与收益不匹配，且会推翻现有"整条匹配一色"契约。
- 不把 105 条规则改成逐条色卡（用户不会点 105 次色卡，改色挂在档/组上）。
- 不用"探针语料 0 命中"当删除依据（§1 的告警）。
- 不动 `config.keywords` 的扁平存储结构，只加字段（`tier`），老配置零迁移。
- **v2 新增**：不做异色规则合并成"一档一色"（§6.1，不减面积只丢区分度）；不在本轮实现结构档限跨度（§7.4）；不在本轮引入 hex 与对比度门槛（§8，批次 4 按实机数据决定）；迁移不做"保留用户改过的色"分支（§3.2，当前 UI 走不到该状态）。
