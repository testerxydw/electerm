# 分析 - 远程页面内存释放与 VNC 刷新期增长 - 2026-11-04

> 起因（用户原话）："检查所有远程页面，在关闭后，是否释放内存，现在怀疑VNC连接页面内容持续刷新时，
> 内存增长过快，并且关闭VNC后，内存不释放，同步检查其他页面的内存释放"
>
> 本轮为只读审计（不改产品代码）。noVNC 版本 1.7.0（`node_modules/@novnc/novnc/package.json:3`）。
> 相关前作：`doc/分析-RDP-VNC窗口自适应与资源开销-2026-10-30.md`（resize 回调链路，其建议 ①②③ 已落地，
> 见本文 §5 "已排除"）；`src/test/unit-ci/remote-session-release.spec.js`（上一批已钉住的释放契约）。

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| VNC **刷新期**涨得快 | 成立，两个来源：① noVNC 接收环形缓冲 `_rQ` 扩容后**永不缩回**（4MiB → 上限 40MiB，`websock.js:316-346`）；② JPEG/Tight tile 逐块 base64 + `new Image()`，一帧内几百块同时驻留，绘制后仍等 GC 才还（`tight.js:85-94` → `display.js:364-381`）。 |
| VNC **关闭后**不释放 | 关闭这条路径本身是干净的（canvas 归零 + disconnect + 解引用都在，见 §3）。用户感知的"不释放"有三个更可能解释：**A 只是切走没关**（隐藏 tab 全量存活，且服务端继续推流）；**B 在异步窗口里关**（子进程滞留 2 分钟）；**C Chromium 不把已释放内存交还 OS**（RSS 台阶不回落，属平台行为）。 |
| 其他页面 | 终端/SFTP/数据库/Web 的**关闭**路径基本都释放；共同病根同 A：**非激活 tab 从不卸载**，代价按页型是"子进程 50–100MB"到"webview guest 进程 50–150MB"。数据库隐藏态还在跑 2s/5s 轮询。 |
| 要不要动 noVNC | ①②都在 vendored 依赖里，我们这层能做的只有"不背锅"的缓解（§4 M2）；结构性修复要 fork 或上游 PR（§4 M5）。 |
| 副产物 | 顺带发现一个与内存无关的功能缺陷：独立 SFTP/FTP tab 的子进程会在 120 秒被兜底定时器误杀（`markConnected` 只覆盖 rdp/vnc/spice/terminals 四条路由），见 §4 SFTP 行与建议 M0。 |

## 1. 结构性事实（决定其余一切判断）

```
sessions.jsx:38   tabs.map(...)                 ← 每个 tab 的会话组件始终挂载
session.styl:51   .session-wrap { display none } ← 只切可见性
                  &.session-batch-active { display flex }
```

- **切走 ≠ 关闭**：切走时组件不卸载、`componentWillUnmount` 不跑、WebSocket 不断、服务端继续按帧推流。VNC/RDP/SPICE 的 `_rQ`、帧缓冲、backbuffer 全部常驻。
- 关闭（`removeTabs` / `closeOtherTabs` / `closeTabsRight` / `reloadTab`）会 splice `store.tabs` 并调 `releaseTabResources`（`src/client/store/tab.js:49-63`），React 必卸载 —— 这条是可靠的。
- 好消息：`sessions.jsx:43-58` 已经把 `activeTabId{batch}` 传给每个会话组件，所以"按可见性降载"不需要新管道（§4 M1）。

## 2. VNC 刷新期增长（会话存续中）

### 2.1 ① 接收缓冲高水位不回落（确定性常驻增长）

`rfb.js:2625-2636`：每收到新 FramebufferUpdate 头，若 `display.pending()` 未清空就置 `_flushing = true`，暂停消费消息队列；但 WebSocket 仍在投递 `_recvMessage`，数据全进 `rQ`。

`websock.js:316-346` `_expandCompactRQ`：扩容规则是"至少当前积压的 8 倍且翻倍"，基线 4MiB（`websock.js:56`），上限 `MAX_RQ_GROW_SIZE = 40MiB`（`websock.js:20`）。**扩容后 `this._rQ = new Uint8Array(this._rQbufferSize)`，消费完游标复位（`websock.js:350-355`）但 buffer 从不缩回**。

刷新越快 → flush 等待越频繁 → 积压峰值越高 → 水位越高；一次 40MiB 的水位在整个会话期间常驻，且每次扩容都留下一份旧 buffer 的垃圾。这是"看着一直涨、涨到某个高度不再涨"的形态。

### 2.2 ② JPEG tile 的 Image/dataURL 洪峰（GC 前显存/图像内存膨胀）

我们默认 `qualityLevel = 3`、`compressionLevel = 1`（`vnc-session.jsx:217-218`）—— 低画质换带宽，服务器更倾向给 JPEG 子编码。路径：`decoders/tight.js:85-94` → `display.js:364-381` `imageRect()`：逐 tile 做 `Base64.encode`（`base64.js:21-40`，逐字符拼大字符串）+ `new Image()` + dataURL，全部 push 进 `_renderQ`（`display.js:482`）；`rfb.js` 只在 FBU 边界 flush，所以**单帧内几百个 tile 的编码串和解码位图同时驻留**。绘制后虽 `a.img.src = ""`（`display.js:526`），Chromium 解码后的位图仍要等 GC 才归还 —— 表现为曲线持续上抖。

### 2.3 ③ 仅当远端反复改分辨率时才成立

`display.js:196-214` `resize()` 每次先 `getImageData` 整屏（1080p ≈ 8MB ImageData），再写 `canvas.width/height` 强制重分配 backbuffer。x11vnc / TigerVNC 正常刷新不会反复发 DesktopSize，所以列为条件项。

### 2.4 ④ 潜在：H.264 路径 `_pendingFrames` 泄漏（只在协商到 H264 时）

Electron 支持 WebCodecs，`rfb.js:2235` 会优先协商 H264；新版 TigerVNC 会给视频区域选它。`decoders/h264.js:121,167-181` 每 chunk push 一个 pending，`decode()` 抛错被 `catch`（`:226-229`）时该 pending 永不 shift，队列无限增长且持有 rQ 的 subarray 引用。另 `h264.js:199-201` 把 `this` 误写成全局 `self`。

### 2.5 已排除（不要重复排查）

| 类别 | 结论 |
|---|---|
| 重复 addEventListener | `vnc-session.jsx:395-412` 每次连接在 RFB 实例上注册 11 个监听器，随实例整体丢弃；`_attachClipboardSync`/`_detach` 成对（`:543-557`）；noVNC 1.7.0 的监听全绑在 `_canvas`/`_screen`，`_disconnect()`（`rfb.js:608-625`）统一移除并 `websock.close()`。 |
| 定时器 / RAF | `rfb.js:731` 的 rAF 与 `_resizeTimeout`/`_mouseMoveTimer` 一次性且 disconnect 时 clear；包装层 `timer`/`screenTimer`/`layoutTimer` 在 willUnmount 清（`vnc-session.jsx:133-135`）。 |
| ResizeObserver 风暴 → canvas 重分配 | 前作 §3.3 的问题已修：`remote-adapt.js:97-106` 防抖 + `shouldReLayout` epsilon，`appliedFit`/`appliedClip` 判等再写 setter，`autoscale` 只写 style 不动 backing store。 |
| 重复建连 | `remoteInit` 只在 mount 与 `handleReInit`（先 disconnect 旧实例）执行；`componentDidUpdate` 只调 `updateViewLayout`。 |
| 日志累积 | noVNC 默认 level `warn`（`core/util/logging.js:16`），Debug/Info 是空函数。 |
| Blob / ObjectURL | VNC 路径无 `createObjectURL` / `toDataURL` / `new Blob`。 |

## 3. VNC 关闭路径（已核实的部分 + 三个残留）

**已经做对的**（`vnc-session.jsx:112-136`，契约在 `remote-session-release.spec.js`）：
先归零 `rfb._canvas` 与 `rfb._display._backbuffer`（实测 2048x1152 时后者约 9MB），再 `disconnect()`，再 `delete this.rfb`；`loadVncModule()` 之后 / `new RFB()` 之前有 `_unmounting` 短路。服务端：每个 VNC tab 独占一个 fork 的 session-server 子进程（`session-process.js:41-59`），ws close → `cleanup()` → `cleanAllSessions()` + 2s 后 `process.exit(0)`（`session-server.js:739-746`）。

**三个真实残留**：

1. **隐藏 tab 不算关闭**（§1）—— 若"关闭 VNC"实际是切走或关掉别的 tab，`store.tabs → Sessions → VncSession → this.rfb → _rQ(4–40MB) + canvas + backbuffer` 整条链存活。**这一项解释力最强。**
2. **异步窗口内关闭 → 孤儿子进程 ≤2 分钟**：`createTerm` 在 `vnc-session.jsx:232` 就已 fork 子进程并拿到 pid，随后关 tab，`_unmounting` 短路（`:259-261`）正确地不再 `new RFB`，于是**这条 pid 的 ws 从未建立** → `ws.on('close') → cleanup()` 不触发 → 只能靠 `noConnectionTimer` 的 2 分钟兜底（`session-server.js:757-763`，日志 `no WS connection within 2min`）。期间白占一份 node 子进程 RSS（数十 MB）。
3. **手动重连（`handleReInit`，`vnc-session.jsx:705-710`）不归零显存**：只 `disconnect() + delete this.rfb`，旧实例的 `_canvas` + `_display._backbuffer` 两份帧缓冲要等 GC；点几次重连就有几份并存 —— 用户视角正是"关了还涨"。
4. 另有平台行为：Chromium 释放后不主动把堆页交还 OS，关一个 tab 后 RSS 常常只降一小台阶甚至持平。判断真泄漏要看 **JS heap（DevTools/CDP `queryObjects RFB`）**，不能只看任务管理器。

## 4. 其他页型（关闭 / 隐藏两态）

| 页型 | 隐藏时保留 | 关 tab 是否释放 | 备注 |
|---|---|---|---|
| 终端 local/ssh/telnet/serial | 子进程（fork，含 pty/ssh2）50–100MB RSS、xterm 实例+scrollback（默认 3000 行，`default-setting.js:10`）、term ws 常开 | **是**（`terminal.jsx:307-339` dispose term/socket/addon；`:350-355` 释放 WebGL 上下文） | "保持会话"是产品语义，不该改成休眠 |
| SFTP | 目录列表 state（大目录数十 MB/侧）、sftp ws + 服务端通道 | **是**（`sftp-entry.jsx:110-119`，`_sortCache` 显式 clear；服务端 `session-sftp.js:55-96` kill） | ①`onDestroySftp` 只 kill 不 `removeSession`（`src/app/server/remote-common.js:36-39`），残留到进程退出；②**FTP/SFTP-only tab 的子进程生命周期是错的**：`markConnected()` 只在 rdp/vnc/spice/terminals 四条路由里调（`session-server.js:99/115/135/159`），而独立 SFTP tab 先用 `createTerm` fork 子进程（`sftp-entry.jsx:136`）、只开 `/sftp/:id` 与 `/transfer/:id`（`session-server.js:519/579`）——两条路由都不置位 → `firstWsConnected` 恒 false → **120s 兜底定时器会 kill 正在使用中的子进程**。这是功能 bug，比内存问题更该先修 |
| 数据库 | 主进程连接池（按 tabId 引用计数，`db-client/index.js:229-312`）、元数据树、结果集 rows、CodeMirror 文档，**以及隐藏 tab 照跑的 2s/5s 事务轮询**（`db-session.jsx:2053-2073`） | **是**，双保险：卸载 effect `closeDbTab`（`:1266`）+ `releaseTabResources`；refs 归零 end pool（`mysql.js:55`/`postgres.js:124`/`redis.js:99`）、SSH 隧道 `inst.tunnel.close()`、`txCloseGuards` 删除 | 四类里最干净；只建议轮询加可见性判断 |
| Web | `<webview>` 的 guest Chromium 进程 50–150MB RSS，页面 JS/定时器/音频/WebSocket 照常跑 | **是**（React 移除元素 → guest 销毁；主进程 `credentialsMap`/`headersMap`/`authRequestMap` 在 `destroyed` 里 delete，`webview-handler.js:87-96`） | **隐藏态最贵、最容易被感知为"内存不回落"的一项** |
| 跨类 | `fileTransfers` 是 `window.store` 上的全局数组，只 push 不 prune（`addTransfers` 见 `src/client/store/transfer-list.js:25-31`），关 tab 与 `releaseTabResources`（`src/client/store/tab.js:49-63`）都不剔除 | **否** | 条目小，但 `isTransporting` 状态会残留 |

## 5. 建议动作（按性价比排序；M0/M2/M6 已落地，其余待定）

| 编号 | 动作 | 命中症状 | 成本/风险 |
|---|---|---|---|
| **M1** | **非 batch-active 的 VNC/RDP/SPICE tab 挂起**：超过宽限期（如 30s）就 disconnect 并归零 canvas，回切时自动重连。注意：`sessions.jsx:58` 把 `currentBatchTabId` 传给了 `Session`，但 `session.jsx:266-283` 的 `rdpProps` 只挑了 7 个键，**并没有**把它转发给 Vnc/Rdp/Spice —— 需要先补这条管道。 | §1、§3.1、"关了还涨" | 中：重连有 1–2s 等待；要保住窗口尺寸/缩放记忆 |
| **M2** ✅ 已实施 | VNC/RDP/SPICE 的 `handleReInit` 复用 willUnmount 的"归零 canvas + 解引用"逻辑，各自抽成 `_releaseRfb` / `_releaseCanvas` / `_releaseCanvases`。 | §3.3 | 低，纯前端；契约测试见 `src/test/unit-ci/remote-session-release.spec.js` |
| **M3** | 异步窗口关闭时**主动销毁已 fork 的子进程**：`componentWillUnmount` 里若已拿到 `this.pid` 而 `this.rfb` 未建，向主进程发一条 abandon（需要新增一条按 pid 销毁的通道，目前 `session-api.js` 没有）。 | §3.2 | 中：要新 IPC；比 2 分钟兜底及时得多 |
| **M4** | Web 页隐藏时降载：非激活则条件渲染卸载 webview（回切 reload）或 `element.detach()` + 静音；数据库事务轮询加可见性判断。 | §4 Web/DB | 中：reload 会丢页面内状态，需要用户决策 |
| **M5** | noVNC ①②：`_rQ` 消费完缩回基线 + JPEG tile 改 `createImageBitmap(Blob)`（与 h264 路径一致）。两处都在 vendored 依赖里，可选 (a) 上游 PR、(b) 随包 patch、(c) 只在文档里记为已知上游行为。 | §2.1、§2.2 | 高：动第三方运行时；M6 已量化，见 §7 |
| **M6** ✅ 已跑 | 量化：见 §7。改用了不依赖 `work/app` 的自建探针（假 RFB over ws + 真 noVNC `/core/*` + headless Edge CDP）。 | 定性→定量 | — |
| **M0** ✅ 已实施 | （审计副产物，与本议题无关但更紧急）给 `/sftp/:id`、`/transfer/:id` 补 `markConnected()`，或让 120s 兜底只在"从未有任何 ws"时生效 —— 否则独立 SFTP/FTP tab 的子进程会在用满 2 分钟时被误杀。 | §4 SFTP | 低：一行一路由；契约测试见 `src/test/unit-ci/remote-session-release.spec.js` 的"子进程兜底定时器"块 |
