# electerm AI 能力优化分析 · AI 写 SQL、AI 输入框支持图片与粘贴图片

分析日期：2026-10-31
分析范围：只读代码，不编译、不跑测试
代码基线：master（工作区含未提交的数据库、终端布局改动，与本文结论无冲突）

---

## 0. 结论先说

本轮要解决的是两件互相独立但可以同一批次落地的事：

1. **让 AI 的产出能真正进入 SQL 编辑器。**
   当前数据库会话页只有一个"让 AI 解释这条 SQL"的单向入口（把整段 SQL 塞进右侧 AI 面板的输入框），AI 回复里的 SQL 代码块只有"复制"和"在终端里运行"两个动作。**缺的不是 AI 能力，而是从 AI 回复回到编辑器的通道，以及从自然语言到 SQL 的生成/修复/优化入口。**
   建议：**"AI 生成 / AI 修复 / AI 优化"走独立的生成弹层（非流式、先预览、确认后插入），AI 对话面板的 SQL 代码块补一个"插入编辑器"动作；两者都不自动执行，仍走现有危险 SQL 确认闸门。**

2. **让 AI 输入框支持图片，并支持直接粘贴图片。**
   当前附件通道明确只收文本文件，图片被主动拒绝；没有 `onPaste` 处理，所以截图粘贴进来是空的。更关键的是：协议层三种协议里只有 OpenAI Chat 能"顺带"通过 content 数组，OpenAI Responses 与 Anthropic 的构造器会把消息压成纯文本，图片会**静默丢失**。
   建议：**分三层落地——输入层（选择/拖拽/粘贴 + 压缩缩略）、协议层（三协议图片分片映射）、存储层（图片二进制不进 AI 历史库）。模型是否支持图片加一个显式配置项，默认自动探测、允许覆盖。**

顺带发现 4 个与本次主题直接相关的既有缺陷，建议一并修掉（见 §5）。

## 1. 现状：AI 链路实际是怎么跑的

### 1.1 右侧 AI 对话面板（src/client/components/ai/ai-chat.jsx）

- 面板组件是 `AIChat`，输入框是 antd `Input.TextArea`，状态在本组件 `prompt` / `attachments` 里。
- 附件通道三条：
  - 回形针按钮 → 隐藏的 `<input type="file" multiple>`（**没有 `accept`**，什么文件都能选，再由读取函数判型）。
  - 整个面板容器 `onDragOver` / `onDrop` → `handleFiles(evt.dataTransfer.files)`。
  - **没有 `onPaste`**，粘贴的图片不会进入 `handleFiles`。
- `handleFiles` 里对每个文件调用 `readTextAttachment`，返回 `error === 'notTextFile'` 就归入 `notText` 并 toast 报错（`ai-chat.jsx:124-152`）。也就是说图片当前是**被设计拒绝**的，不是没实现。
- 附件的展示是一排 antd `Tag`，只有回形针图标 + 文件名（`ai-chat.jsx:396-409`），没有任何预览能力。
- 提交时把附件内容拼成一段文本块塞进 prompt：`buildAttachmentsBlock(attachments)` → `promptWithAttachments`（`ai-chat.jsx:166-208`）。**这是纯字符串，天然容不下图片。**
- 面板把自己注册进全局引用表 `refsStatic`，只暴露两个方法：`setPrompt` 和 `handleSubmit`（`ai-chat.jsx:316-324`）。外部（终端、数据库页）能做的只有"填一段文字然后替你按回车"。

### 1.2 附件模块（src/client/components/ai/ai-attachments.js）

文件头注释就写明了策略：

> only text files are supported: content is read and inlined into the prompt, images/binaries are rejected

- 单文件上限 50 KB，全会话附件总上限 100 KB（`ai-attachments.js:6-7`）。
- 判型方式是嗅前 8 KB：出现 NUL 字节即判二进制，控制字符占比 > 10% 也判二进制（`ai-attachments.js:13-29`）。图片必然被这里拦掉。
- `buildAttachmentsBlock` 把每个文本附件包成 `<file name="...">…</file>`（`ai-attachments.js:78-87`）；文件名只做了双引号转义，**没有防 `</file>` 提前闭合**（注入面，见 §5.6）。
- 去重规则是 `name + size` 相同就跳过（`ai-chat.jsx:129-131`）。截图文件名几乎都是 `image.png`，同尺寸重复粘贴会被误判为"同一个附件"。

### 1.3 会话消息构造与上下文估算（src/client/components/ai/ai-context.js）

- `buildSessionMessages` 把历史条目摊平成 OpenAI 风格的 `messages`，每条 turn 产出 `{ role: 'user', content: 字符串 }` 与 `{ role: 'assistant', content: 字符串 }`（`ai-context.js:176-201`）。user 侧优先取 `promptWithAttachments`，兼容老数据回退 `prompt`。
- token 估算 `estimateMessagesTokens` 直接对 `m.content` 走字符串估算（`ai-context.js:44-67`）。**如果 content 变成数组，`String(content)` 会得到 `"[object Object]"`——上下文指示器会算错，压缩判断也会错。** 这一点必须先改，否则"带图的那一轮"会被系统当成几乎没占上下文，直冲 provider 的硬上限。

### 1.4 协议层（src/app/lib/ai-format.js）

支持三种线上协议，由 API path 探测：`/chat/completions` → OpenAI Chat，`/responses` → OpenAI Responses，`/messages` → Anthropic。

- `buildOpenAIChatBody`（`ai-format.js:137-147`）原样透传 `messages`。**这是三家里唯一现在就能吃 content 数组的。**
- `buildResponsesBody`（`ai-format.js:150-219`）对 user 消息做的是 `content: textFromContent(m.content)`，而 `textFromContent`（`ai-format.js:60-83`）只认 `part.text` / `part.content`。**图片分片会被直接丢掉，不报错。**
- `buildAnthropicBody`（`ai-format.js:222-309`）对 user 消息固定生成 `[{ type: 'text', text: textFromContent(m.content) }]`。**同样静默丢图。**
- 结论：图片能力必须在这一个文件里做**分协议的 content 映射**，不能只在渲染层拼字符串。

### 1.5 AI 历史落库（src/client/store/watch.js + src/client/common/db.js）

- `aiChatHistory` 是需要落盘的集合之一（`db.js:26-51`），由通用 watcher 做增量 diff 后写 NeDB/SQLite（`watch.js:23-84`）。
- 针对 `aiChatHistory` 已经专门做了 1 秒 debounce，原因写在注释里：流式回答每 200ms 一次 tick、agent 每个工具结果都会写一次。
- 但**每次写的是完整条目对象**。如果把图片 base64 放进条目，那么流式期间的每一次回答更新，都会把这张图的 base64 重新序列化、重新 diff、重新写盘一遍；`deepCopy` 快照同样跟着放大。历史上限是 500 条，最坏情况数据库会到几百 MB 量级。**这是"图片附件"最容易被忽略、也最先炸的环节。**

### 1.6 数据库会话页与 AI 的联动（src/client/components/database/db-session.jsx）

现有唯一一个入口：SQL 工具栏上的闪电图标 → `askAiAboutSql(sqlText)`（`db-session.jsx:7625-7638`，函数体 `3489-3507`）。它做的事情是：

1. 打开右侧 AI 面板（`window.store.handleOpenAIPanel()`）；
2. `setTimeout(500)` 往 `refsStatic.get('AIChat')` 里 `setPrompt('请解释以下 SQL 语句：…')`；
3. `setTimeout(1200)` 再调 `handleSubmit()`。

这条路径的问题：

- **只有"解释"，没有"生成 / 修复 / 优化"**。
- **传的是整段编辑器内容**，尽管编辑器组件本身已经暴露了 `getSelectionText()`（`db-sql-editor.jsx:316-323`）；选区场景（只想问一句里的某一段）没利用。
- **不带任何上下文**：方言（`tab.dbType`）、当前库、当前选中表及其列结构（`structureV2.columns`）、是否只读连接都没带上。同一个问题在 MySQL 和 PostgreSQL 下答案不同，模型只能猜。
- 提示词是**硬编码中文**，与 AI 配置里的回复语言无关。
- 依赖两个魔法延时。终端侧的 `explainWithAi`（`store/common.js:457-466`）是同一套写法，同一个脆弱点。
- **单向**：AI 回答完了，没有任何机制把 SQL 送回编辑器。

SQL 执行失败的展示更直白：结果区顶部只有一个 `<Alert type='error' showIcon message={sqlResult.error} />`（`db-session.jsx:7756-7761`），没有"复制错误"，也没有"让 AI 修"。

反过来，AI 侧的输出组件（`src/client/components/ai/ai-output.jsx:41-99`）给每个代码块提供两个动作：复制到剪贴板、在终端里运行（`window.store.runCommandInTerminal`）。**对一段 SQL 而言，"在终端里运行"是错误动作**——它会把 `SELECT * FROM …` 直接送进 shell。而对 SQL 真正需要的"插入到当前 SQL 编辑器"根本不存在。

顺带说明可行的一侧其实已经齐了：数据库会话页持有 `sqlEditorRef`，编辑器句柄上有 `getValue()` / `getSelectionText()` / `insertText(text)`（`db-sql-editor.jsx:304-366`），页内已经有统一插入函数 `insertToEditor(text)`（`db-session.jsx:3153-3160`，走 CodeMirror `dispatch`，保留撤销栈、光标落文本尾）。收藏、模板、复制为 INSERT 都通过它回写编辑器。**"AI 写 SQL"缺的只是把这条既有通道接到 AI 侧。**

### 1.7 Agent 模式的工具集（src/client/components/ai/agent-tools.js）

26 个工具全部围绕终端 / 书签 / SFTP（`agent-tools.js:29-467`），执行分发在 `executeToolCall`（`agent-tools.js:469-540`）。**没有任何一个数据库相关工具**，agent 甚至不知道当前有一个已连接的 SQL 会话。Agent 模式在数据库页里只能"聊天"，不能做事。

### 1.8 AI 配置项（src/client/components/ai/ai-config.jsx + src/app/common/default-setting.js:76-83 + ai-config-props.js）

现有字段：`nameAI` `baseURLAI` `modelAI` `roleAI` `apiKeyAI` `authHeaderNameAI` `apiPathAI` `languageAI` `proxyAI` `contextLengthAI`。**没有任何与"模型是否支持图片/视觉输入"有关的字段**；AI 预置服务商列表（`ai-presets.js`）也没有能力元数据。想支持图片，配置层要补一项并同步 `aiConfigsArr` / `optionalAIConfigsArr` / 设置同步白名单。

## 3. 方案一：让 AI 把 SQL 写进编辑器

### 3.1 目标与非目标

目标：

- 自然语言 → SQL，结果**只填进编辑器**，绝不自动执行。
- 执行失败 → 一键"AI 修复"，把 SQL + 方言 + 表结构 + 错误原文一起交给模型，结果可预览、可替换。
- 选区/整段 → "AI 优化"（重写、加索引建议、修写法）。
- AI 对话面板回复里的 SQL 代码块 → 一键插入当前数据库会话页的编辑器。
- 以上全部沿用既有安全闸门（危险 SQL 分级 + 生产连接确认 + 只读连接拦截），AI 不新增任何绕过路径。

非目标（本轮明确不做）：

- AI 自动执行 SQL。
- AI 直接改表结构 / 直接写数据（DDL/DML 落库）。
- Agent 模式获得写库工具（放到 §5.5 单独评估）。

### 3.2 为什么建议"生成走弹层、对话走代码块动作"，而不是全部塞进 AI 面板

沿用最开始的设想（复用右侧 AI 面板 + `setPrompt` + `handleSubmit`）有一个绕不开的结构性问题：**当前 AI 面板的请求链路没有"返回通道"。** 一次提交产出的只是一条历史记录，回答落在 `aiChatHistory` 里；要把回答送回编辑器，必须给每条 turn 挂"目标 tab + 插入策略"，再在流式结束时做解析和派发，并处理"目标 tab 已关闭""期间又发了新消息"等情况。再加上现有 `setTimeout(500/1200)` 那套脆弱时序，复杂度全部落在**共享的对话链路**上，回归面很大。

项目里已经有两条成熟的同类做法可以直接对齐：**快捷命令 AI 生成器**（`src/client/components/quick-commands/quick-command-ai-editor.jsx:164-204`）和**书签 AI 生成器**（`src/client/components/bookmark-form/ai-bookmark-form.jsx`）。它们的共同点是：描述输入 → 非流式 `AIchat` → 解析 → **预览 + 用户确认** → 落到目标对象。这个模式天然满足"AI 不自动执行、人先看再落"的要求，也不动对话链路。

因此建议：

- **一次性、结构化的产出（生成 / 修复 / 优化）→ 独立弹层。** 有预览、有确认、有取消，不需要把会话语义拖进来。
- **对话式的追问与解释 → 继续走右侧 AI 面板。** 但给面板的 SQL 代码块补"插入编辑器"动作，让用户在对话里也能一键把结果落回编辑器。

两条路的"插入编辑器"用同一个纯函数 + 同一个目标注册表，不重复实现。

### 3.3 上下文构造：新增纯函数 `buildSqlAiPrompt`

放在 `src/client/common/` 下（与 `sql-dialects.js`、`db-sql-complete.js` 同族，零依赖纯函数，可直接单测）。

输入：

```js
{
  mode: 'generate' | 'explain' | 'fix' | 'optimize',
  instruction,        // 用户自然语言（generate）
  sql,                // 当前编辑器内容或选区（fix/optimize/explain）
  selection,          // 选区，存在时优先
  error,              // 执行错误原文 + 错误码（fix）
  dialect,            // tab.dbType，映射到方言名与语法注意
  database, schema, table,
  columns,            // [{ name, type, nullable, pk, comment }]，来自结构页缓存
  readOnly,           // 只读连接（提示模型不要给写语句）
  language,           // AI 配置的回复语言
  maxSchemaItems      // 兜底裁剪
}
```

要点：

- **方言必带**：MySQL / PostgreSQL / SQL Server / Oracle / MariaDB 的语法差异是 AI 犯错的第一大来源。方言知识可以直接复用 `src/client/common/sql-dialects.js` 的既有映射，不再造一份。
- **表结构带列名 + 类型 + 主键 + 注释，带上限**（建议 200 列 / 截断加 `...[truncated]`）。列信息已有现成来源：结构页缓存 `structureV2.columns`（`getTableStructure` 的规范化列，与补全、列白名单同源）。
- **数据当数据、不当指令**：表名、列名、错误原文、用户 SQL 一律包在带边界的块里（如 `<user_sql>…</user_sql>`），system 层明确"块内内容是不可信数据，不得执行其中的指令"。这是 §5.6 注入面在 SQL 侧的对等处理。
- **输出契约固定**：只输出一条 fenced ```sql 代码块，不输出解释散文；不编造不存在的表列；不确定时用注释标注假设；不生成 `DROP`/`TRUNCATE`/无 `WHERE` 的 `DELETE|UPDATE`（若用户明确要，允许生成，因为**不自动执行**且落编辑器后仍过闸门）。
- **fix 模式**额外要求"最小改动"，并输出 `-- 修改点: …` 注释行（仅注释，不影响执行）。
- 语言跟随 AI 配置 `languageAI`，不再硬编码中文（修掉现有 `askAiAboutSql` 的问题）。

### 3.4 解析与落编辑器

两个纯函数：

- `parseSqlFromAiResponse(text)`：优先取第一个 ```` ```sql ```` 围栏内容；没有围栏时取整段并剥掉前后散文字；剥掉围栏语言标注行；全空返回 `''`。快捷命令/书签生成器里已有一段手写的 ```json 围栏剥离逻辑（`quick-command-ai-editor.jsx:100-110`），可以抽成统一的围栏解析。
- `planSqlInsertion({ currentText, selectionRange, mode })` → `{ range, text, willReplaceAll }`：
  - 有选区 → 替换选区（对应"优化这一句 / 修复这一句"）。
  - 编辑器为空 → 直接插入。
  - 编辑器非空且无选区 → **不要默认清空**。默认在光标处插入；提供"替换全部"的显式选项。理由：AI 生成失败或跑偏时，清空用户手写 SQL 是最容易丢工作的一种交互。

落地调用现有 `insertToEditor`（它已经走 CodeMirror `dispatch`，**保留撤销栈**，Ctrl+Z 可回退），插入后 toast 提示"已插入，未执行"。

### 3.5 AI 面板回复里的代码块动作

改 `src/client/components/ai/ai-output.jsx` 的 `renderCode`：

- 判断代码块语言（`language-sql` / `language-mysql` / `language-postgres`，或用 `classifySql` 的前缀试探兜底）。
- 判断当前活动 tab 是否数据库会话（用现成守卫 `src/client/common/db-engine-mark.jsx` 的 `isDbSession`）。
- SQL 代码块 + 活动 tab 是数据库会话 → 主按钮"**插入编辑器**"，次按钮"复制"，**隐藏"在终端运行"**。
- SQL 代码块但当前不是数据库会话 → "插入编辑器"禁用并给出原因提示；保留"复制"；终端运行仍然隐藏（对 SQL 没意义）。
- 非 SQL 代码块 → 行为完全不变（复制 + 终端运行），避免影响终端主场景。

目标定位：

- 数据库会话页挂载时把编辑器句柄注册到一个按 tab id 索引的表里（项目已有 `refsStatic` 机制，AI 面板自身也这么注册；或复用 `src/client/store/tab.js:102` 里"关闭前守卫由 db-session 注册"的同类做法）。注册内容建议是 `{ insertSql(text, plan), getContext(), isReadonly }`，卸载时反注册。
- AI 面板只按 `store.activeTabId` 找目标；找不到就禁用动作，不做"自动切到某个数据库 tab"这种带副作用的行为。

### 3.6 入口与安全闸门的关系

- 生成弹层与"AI 修复"都只调用 `insertText` 级别的编辑器 API，**不触碰 `runSql`**（`db-session.jsx:2694-2710`）。
- 用户按执行后，仍然走 `confirmSqlRisk`（`db-session.jsx:2495-2528`）：危险语句分级、生产连接确认、需要输库名的高危项、只读连接由主进程白名单二次拦。AI 不获得任何新的执行路径，也不新增"记住本次选择"的旁路。
- 预览弹层里额外显示这条 SQL 的风险分级结果（复用 `classifySql`），让用户在**插入前**就知道"这段是要落库的写操作"，而不是插完按下执行才被弹窗打断。

## 4. 方案二：AI 输入框支持图片 + 粘贴图片

### 4.1 现状断点复述

1. 附件读取层拒绝图片（`ai-attachments.js:1-7`）。
2. 输入层没有 `onPaste`（`ai-chat.jsx:410-417`）。
3. 提交层把附件摊平成字符串块（`ai-chat.jsx:166-208`）。
4. 消息构造层 content 恒为字符串（`ai-context.js:176-201`）。
5. 协议层两家会静默丢图（`ai-format.js:150-219, 222-309`）。
6. 估算层不认数组（`ai-context.js:44-67`）。
7. 持久化层整条重写（`watch.js:23-30`）。
8. 配置层无视觉能力位（`ai-config.jsx`）。

**图片能力不是加一个 `<input accept="image/*">`，而是要把"图片"这个概念贯通这 8 层。** 建议按下面 5 组改动来做。

### 4.2 输入层：选择 / 拖拽 / 粘贴

**文件选择**：隐藏 input 加 `accept="image/png,image/jpeg,image/webp,image/gif,text/*,application/json,…"`（保留文本附件能力，不回归）。

**拖拽**：现有 `onDrop` 已经能拿到 `dataTransfer.files`，只需让 `handleFiles` 按类型分派。注意：从浏览器拖图片会带 `text/uri-list`，`dataTransfer.files` 为空；本期**不做远程 URL 抓取**（涉及隐私、CORS、SSRF 面），只提示"请拖本地文件或先保存再粘贴"。

**粘贴（重点）**：给 TextArea 加 `onPaste`：

- 遍历 `evt.clipboardData.items`，凡 `kind === 'file'` 且 `type.startsWith('image/')` → `getAsFile()`，收集。
- **有图片项时才 `preventDefault()`**；纯文本粘贴必须保持原生行为不变（这是最容易做坏的地方——一刀切拦截会让粘贴文字失效）。
- Linux 截图工具（deepin 截图、flameshot、gnome-screenshot）在剪贴板里通常同时放 `Files` URI 和 `image/png` bitmap。所以**两个来源都要读**：先读 `items`（bitmap），再补 `clipboardData.files`（URI 形式）；用内容哈希去重，避免同图入两次。
- 若同时存在图片和文本（例如从表格/网页复制），默认收图片并把文本作为 prompt 追加；不要把文本丢掉。
- Electron 主进程的 `window.pre.readClipboard()` 目前只读文本（`src/app/lib/ipc-sync.js:50-52`）。渲染层粘贴事件足以覆盖截图场景，**本期不建议动主进程剪贴板 API**。
- 名称兜底：无文件名时用 `pasted-<序号>-<时间戳>.<ext>`，别再用浏览器给的 `image.png`（配合 §5.4 的去重改造）。

### 4.3 数据模型：附件区分 kind，图片二进制不进历史

建议的附件对象（内存态）：

```js
{
  id,
  kind: 'text' | 'image',
  name,
  bytes,                 // 压缩后的字节数
  originalBytes,
  mime,                  // image/png | image/jpeg | image/webp | image/gif
  width, height,         // 压缩后的实际尺寸，token 估算要用
  thumbDataUrl,          // ~96px 缩略图，小（3-8KB），可以进历史
  dataUrl,               // 完整 data URL，只存在于内存/缓存，不进历史
  expired?: boolean      // 重启后缩略图还在、原图没了
}
```

历史条目里只留 `id / kind / name / bytes / mime / width / height / thumbDataUrl / expired`。发送时由一个解析器把 `id` 换成 `dataUrl`。

**为什么必须这样拆：**

- `aiChatHistory` 落库且流式期间高频整条重写（§1.5）。图片 base64 进条目 = 每个流式 tick 重写一次几百 KB 到几 MB；`deepCopy` 快照与 `dataCompare` 也跟着放大。500 条上限下数据库体积完全不可控。
- 缩略图很小，保留它能让历史记录在重启后仍然"看得出当初贴了什么"，代价可控。
- 因此图片本体用**独立缓存**存放：
  - **阶段一（先落地）**：进程内 `Map<id, dataUrl>`，加总量预算（例如 20 MB）与 LRU 淘汰；重启即失效，历史条目标 `expired: true`，UI 明示"图片已过期，如需继续使用请重新粘贴"。**实现最小，风险最小。**
  - **阶段二（可选）**：持久化到应用数据目录下的独立图片缓存（项目已有同类做法：会话日志、SQL 历史/收藏/视角配置都走 `app.getPath('userData')` 下的固定文件，见 `src/app/lib/ipc.js:291-360`；渲染层也有 `window.fs.readFileAsBase64` 可用）。需要新增配额与 GC（历史删除 / 清空 / 超预算时回收），并把读取做成异步。
  - **明确不建议**：把完整 data URL 塞进 `aiChatHistory` 或 `localStorage`。

### 4.4 图片预处理（决定成败的一层）

发送前统一走 `normalizeImage(file)`：

1. 解码：`createImageBitmap(file, { imageOrientation: 'from-image' })`，尊重 EXIF 方向。
2. 尺寸钳制：长边 ≤ **1568 px**（Anthropic 明确建议值；OpenAI 高细节也按 512/768 分片，超尺寸只会白烧 token）。原始尺寸过大时等比缩小。
3. 像素上限：拒绝超过 ~4000 万像素的输入（解压炸弹防护）。
4. 重编码：截图/带透明通道的走 `image/webp`（质量 0.85，Chromium 支持良好，Anthropic/OpenAI 都接受 webp）；已有损 JPEG 走 JPEG 保结构。**重编码顺带剥掉 EXIF/GPS 元数据，这是一个隐私正收益，应在 UI 提示里写明。**
5. 体积上限：压缩前单文件 ≤ 5 MB，压缩后单张 ≤ 1 MB，单条消息 ≤ 4 张，单次会话图片总量 ≤ 8 MB。超限给可读错误，不静默截断。
6. 类型白名单：png / jpeg / webp / gif。**SVG 不进图片通道**（本质是 XML，含脚本风险，且各家视觉模型支持不一）；HEIC 这类 Chromium 解不动的格式，解码失败就明确报错。
7. 动图：GIF 动画转静态首帧并提示（视觉模型本就按帧/静态处理）。
8. 缩略图：96–128 px，单独生成，用于附件条与历史展示。

**上限数值要与文本附件分开**：现有 50 KB / 100 KB 是文本预算（`ai-attachments.js:6-7`），不能拿来卡图片；也不能让 `validateAttachmentTotal` 用"原始体积"卡压缩后的图片（会误拒大图）。建议把"预算校验"移到压缩之后，按 `bytes` 计。

### 4.5 消息形态与协议映射（必须三家都改）

`buildAttachmentsBlock` 保留，只负责文本附件；新增 `buildMessageContent({ prompt, textAttachments, imageAttachments })`：

```js
// OpenAI Chat
[
  { type: 'text', text: promptWithTextBlocks },
  { type: 'image_url', image_url: { url: 'data:image/webp;base64,…' } }
]

// OpenAI Responses
[
  { type: 'input_text', text: promptWithTextBlocks },
  { type: 'input_image', image_url: 'data:image/webp;base64,…' }
]

// Anthropic
[
  { type: 'text', text: promptWithTextBlocks },
  { type: 'image', source: { type: 'base64', media_type: 'image/webp', data: '<b64>' } }
]
```

改法集中在 `src/app/lib/ai-format.js`，新增两个纯函数 `mapUserContentTo(format, content)` 与 `hasImagePart(content)`：

- `buildOpenAIChatBody`：原样透传即可（已经是数组安全的路径），但要保证 `withReasoningPlaceholder` 的展开不破坏数组 content（`ai-format.js:126-135`，目前用 `{ ...m }`，是安全的）。
- `buildResponsesBody`：user 分支不再 `textFromContent`，改走映射；`system/assistant/tool` 仍走 `textFromContent`（这三类不会有图）。
- `buildAnthropicBody`：user 分支产出 content 块数组；注意 Anthropic 会把**同一 role 的相邻消息合并**（`pushMessage` 逻辑 `ai-format.js:226-235`），图片块必须跟着合并，不能各自成一条。
- 未知/不支持的 part → 转成 `[unsupported attachment: name]` 文本，绝不静默丢。
- 三家共用 `AIchat`（流式与非流式）与 `AIchatWithTools`（agent），都经由 `buildRequest`，**所以协议层改一次即可全链路生效**。

> 需要实机确认的点：Responses 的 `input_image` 在部分网关上是字符串 `image_url` 还是 `{url:…}` 对象；OpenAI 兼容网关（各家 relay）对 content 数组的支持差异很大。这类差异**必须靠真实 provider 验证**，不能靠猜——建议实现时同时留一个"以纯文本降级发送"的分支（把图片以 `[attached: name]` 形式写进 prompt），provider 报 400 时给用户一次降级机会。

### 4.6 token 估算与自动压缩

`src/client/components/ai/ai-context.js`：

- 新增 `estimateContentTokens(content)`：字符串走现有 `estimateTokens`；数组分别累加；图片按尺寸估（Anthropic 官方近似 `(width*height)/750`，保守取 `max(85, ceil(w*h/750))`）。
- `estimateMessagesTokens` 改用它（`ai-context.js:54`）。
- `buildSessionMessages` 在条目带图片时产出数组 content（经解析器把 `id` 换成 data URL；`expired` 时替换为文本占位 `[attached image unavailable]`）。

压缩链路（`ai-auto-compress.js` / `ai-compress.js` / `store/common.js:539-648`）：

- 摘要请求**剥离图片**，用 `[user attached N images]` 文本代替。理由：摘要本来就是"把长对话压小"，把几百 KB 图再发一遍与目的相反；而且摘要请求走的是非流式纯文本路径（`ai-compress.js:29-52`）。
- `applySummary` / `compactAskMessages` 对数组 content 无需特殊处理（它们保留 system 与 pending turn 原样），但 `splitPendingTurn` 的"最后一条 user"判断要保持数组可用（`ai-auto-compress.js:57-66`，只判 role，是安全的）。
- 上下文指示器（`ai-context-indicator.jsx`）应能显示"图片 N 张 ≈ M tokens"，否则用户无法理解为什么带图后立刻变红。

### 4.7 UI：附件条、缩略图、能力提示

- 输入框上方附件区从 `Tag` 列表升级为"文本用 Tag、图片用小卡片"：缩略图 + 名称 + 尺寸（`宽×高`）+ 压缩后体积 + 删除；点击缩略图出预览大图。图片卡片建议 64 px，一行 wrap。
- 历史条目侧（`ai-chat-history-item.jsx:321-334`）同样支持缩略图展示与预览；`expired` 显示灰色占位 + 提示文案。
- 输入区加一行弱提示：`Enter 发送 / Shift+Enter 换行 / 可直接粘贴截图`（与现有 send icon 的 title 一致，避免只有 tooltip 才发现）。
- 带图但未开启视觉能力时：发送按钮旁给出明确阻断信息与"去设置"的链接，**而不是把请求发出去等 provider 报错**。
- 隐私提示：AI 现有 `aiWarn` 提示（`ai-config.jsx:303-309`）需要补一句"粘贴的图片会上传到你配置的 AI 服务商"。

### 4.8 配置：视觉能力开关

新增 `supportsImageAI`（建议 `'auto' | 'on' | 'off'` 三态，默认 `auto`）：

- `auto`：按模型名做启发式判断（gpt-4o/4.1、gpt-5 系、claude-3 及以后、gemini 全系、qwen-vl、glm-4v 等；纯 deepseek-chat / 小尺寸 llama 视为不支持）。启发式仅供默认值，**不作为唯一依据**。
- `on` / `off`：用户显式覆盖。
- 落点（缺一不可）：`src/app/common/default-setting.js:76-83` 默认值、`src/client/components/ai/ai-config-props.js` 的 `aiConfigsArr` + `optionalAIConfigsArr`（否则会被 `aiConfigMissing` 误判成未配置而反复弹设置窗）、`ai-config.jsx` 表单控件、`ai-chat.jsx:184-194` 的 `pick(props.config, […])`（每条历史要记住当时的能力位，重放才不会变）、`store/sync.js:937` 附近的同步白名单。

### 5.5 Agent 模式的数据库工具 ✅ 已落地（2026-11-03，S2-1）
最小集合建议：`db_get_context`（当前连接/方言/库/选中表）、`db_list_tables`、`db_describe_table`、`db_read_result`（当前结果集前 N 行）、`db_insert_sql`（只写编辑器，不执行）。**不做 db_execute_write**。理由：Agent 已有"直接跑命令"的能力面，再加"直接写库"会把风险从"人看一眼终端"升级到"人看不见 AI 干了什么"。`db_insert_sql` 保留人的确认环节，且天然复用 §3.6 的闸门。落点在 `agent-tools.js:29-467`（schema）与 `469-540`（分发），系统提示词 `agent.js:29-49` 需同步说明能力与边界。

> **落地说明（2026-11-03）**：五个工具全部按本节的最小集接进循环（schema `agent-tools.js:470-580`、分发 `:655-664`、系统提示词 `agent.js:42-44`），边界与本节判断一致。三点补充设计：
> 1. **整形层独立成纯模块** `src/client/common/db-agent-tools.js`——工具返回的 JSON 原样进上下文窗口，"把结果集整表 stringify"一轮就能吃掉大半窗口，还会顺带拖进二进制列与超长文本。行上限默认 20 / 最多 50，单元格 200 字，表清单 200 / 500，列 120；截断一律如实标 `truncated` / `hasMoreRows` / `truncatedCells`，缺省值不当 0（`Number(null) === 0` 会把"没统计行数"读成"这表是空的"）。
> 2. **页签解析不猜**：显式 `tabId` > 活动页签 > 唯一数据库页签；多个候选且活动页签不是数据库时报错列出候选、要求显式给 `tabId`。
> 3. **`db_insert_sql` 只允许 `cursor` 策略**：`replace` / `selection` 不给 agent 用——清空用户手写的 SQL 永远是显式选择；返回值固定带 `executed: false` 与"由人运行、危险 SQL 闸门照旧"的提示。
> redis 页签单独处理：`db_get_context` 如实给上下文但标 `supportsSql: false`（模型据此换路子），对它要表清单直接拒绝，不拿键名冒充表名。
> 验证：单测 `src/test/unit-ci/db-agent-tools.spec.js` 22 例（含四条源码契约：五个名字在 schema 与分发里成对出现、agent-tools 无 `executeSql` 与写库工具名、只读段不含写 op 字面量与 `strategy: 'replace'`、提示词写明 "no tool that runs SQL"）；实机 `self-test/agent-db-tools-demo.js` **36/36 PASS**——真实 agent 回合里五个工具全部 `completed`、整形后的 JSON 以 5 条 `role:'tool'` 回灌、发给模型的 schema 恰好含这五个 db 工具且无执行类，`executeSql` 计数始终等于"人按的那一次 Run"。
