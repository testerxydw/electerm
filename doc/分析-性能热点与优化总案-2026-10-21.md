### 一、总体判断

1. **最大性能杠杆在"每渲染深拷贝/重建"**：`store.config` 等 getter 每次访问 deepCopy 整份配置/列表/树，而渲染层到处读它们 → store 任何变化引发的渲染都在产生大垃圾，GC 锯齿即"内存大涨大跌"。
2. **第二大杠杆在传输进度链路**：进度写入 store 数组（manate 代理）→ 波及 main/sidebar 全树重渲染 + main.jsx render 内整列表 deepCopy；FTP 服务端甚至无节流。
3. **基础面不差**：SFTP 文件列表、书签树已虚拟化（自研）；command-palette 已 useMemo；sftp/zmodem/trzsz 传输进度已节流；xterm 写入有合批。优化应聚焦上面两个杠杆，不必大动干戈。

### 三、优化设计

#### 批次一（P0：低风险高收益，1~2 天）

1. **main.jsx 去 deepCopy + memo**：
   - `upgradeInfo/resolutions/terminalInfoProps` 直接读（只读语义）或 `useMemo`；
   - `fileTransfers/transferHistory` 用 `useMemo(..., [对应 store 字段引用])`？——manate 代理数组引用稳定但内容可变，**不可靠**。改法：deepCopy 移出 render（放到传输更新回调里一次性做），或给渲染层传"只读快照版本号"驱动 useMemo。**推荐**：main.jsx 不再 deepCopy，改为透传代理 + 下游组件用 `auto` 细粒度订阅（transports-ui-store 本就是 auto 组件）。
   - 验收：CDP 渲染计数（React Profiler）传输期间 main 渲染耗时下降；堆采样平稳。
2. **FTP 进度节流对齐**：`ftp-transfer.js` `onData = _.throttle(..., 500)`（与 xmodem 同档）。1 行。
3. **shortcut-control 补卸载清理**：componentWillUnmount removeEventListener ×3。防泄漏。

#### 批次二（P1：tabs 测量与重建，半天）

4. `measureWrapWidth` 改为：ResizeObserver 观察容器 + 仅 `tabs.length` 或窗口尺寸变化时重测；`getSortedTabs` 结果按 `tabs.map(t=>t.id).join()` 签名缓存（类组件用实例字段）。
5. renderExtra Dropdown items 仅在"溢出"状态下构建，且 items 用签名缓存。
- 验收：store 高频更新（传输）期间 tabs 区不再触发出测量/Dropdown 重建（打点确认）。

#### 批次三（P1：getter 签名缓存，1 天，需回归）⬜ 待排期（仅 config 快照已做 `6bd07fd3`，下列 getter 均未做）

6. 对 `config/getSidebarList/settingSidebarList/bookmarkTree/bookmarkGroupTree/currentQuickCommands/quickCommandTags/uiThemeConfig` 引入**签名缓存**：以底层数据的轻量签名为 key，未变则返回上次构建的对象。
   - ⚠️ 语义变化：消费方拿到**同一对象引用**——凡消费方直接 mutate 返回值的地方会污染缓存。实施前先 grep 调用点确认无写操作；对 `config` 这类高频读可先只做 `useKeywordPatterns/getThemeConfig` 已修的两个点 + 渲染层新增 `configRef()` 只读通道，setter 表单等仍走旧 getter（保拷贝语义）。
   - 验收：`npm run test-unit-ci` + 设置页/书签树/主题切换/搜索全回归。

#### 批次四（P2：轮询与 IO，半天）✅ 已完成（8 VNC gate / 9 watch-file / 10 instance-log / 11 历史分页 / 7 AI 轮询卸载守卫 / 12 tooltip rAF 节流 全部落地）

7. AI 流轮询：流结束时停止；`scrollIntoView` 驱动替代内容轮询（或至少加最大时长）。
8. VNC checkScreens：`document.hidden`/面板可见性 gate。
9. watch-file：记录上次 size/mtime，只读增量 tail 再发。
10. instance-log：appendFileSync → appendFile。
11. transfer-history Table：分页（pageSize 50）或虚拟化。
12. unix-timestamp-tooltip mousemove：rAF 节流。

#### 暂不动（刻意设计，记录防误改）

- xterm 10ms 合批 + >16KB 直发、idle/keepalive 轮询、fit 节流 200ms、大快照一次性 write；
- SFTP/书签树自研虚拟化、command-palette 的 useMemo；
- transfer 进度服务端 3s/500ms 节流（FTP 对齐后全链路已受控）。

### 九、实测内存剖析（2026-10-15，运行中的最新版安装实例）

#### 9.1 进程拓扑与占用（用户观察：一个 310M、其他 150M 内 → 复测时主进程已涨到 508M）

| 进程 | 数量 | RSS | **PSS（真实占用）** | 角色 |
|---|---|---|---|---|
| 主进程（browser） | 1 | **508MB** | **320MB** | 窗口/store/IPC 枢纽 |
| renderer | 1 | 288MB | 202MB | 全部 UI：React 树 + xterm 实例 + DOM |
| server.js（中继） | 1 | 131MB | 49MB | ws 中继 |
| **session-server** | **5** | **~124MB each（620MB）** | **~45MB each（225MB）** | **每个 SSH 会话一个 Node 子进程** |
| network utility | 1 | 86MB | — | Chromium 网络服务 |
| zygote ×3 | 3 | ~131MB | — | Chromium 孵化器 |
| 合计 | 13 | **~1870MB RSS** | **≈800MB** | |

#### 9.2 关键结论

1. **"大涨大跌"主因 = session-server 按 SSH 会话增减**：每开一个 SSH 会话立增一个 Node 子进程（RSS +124MB / PSS +45MB），关闭即回落。5 个会话就是 620MB RSS / 225MB PSS 的波动幅度。
2. **任务管理器看 RSS 会重复计数**：每个子进程 RSS 含 ~90MB 共享框架库（Shared_Clean），13 个进程重复计了 ~700MB。真实增量请看 PSS（`smem` 或 `/proc/<pid>/smaps_rollup`）。
3. 主进程 508MB RSS 的构成：**文件映射 136MB**（Electron 框架/asar/ICU，固定不可控）+ **共享内存 123MB**（与 renderer/GPU 的 mojo IPC 缓冲，随渲染活动波动）+ 私有仅 61MB（主进程 JS 堆很小）。RSS 大 ≠ 主进程泄漏。
4. renderer 私有 142MB（Pss_Anon）= JS 堆 + xterm scrollback 缓冲 + DOM——与打开的终端数量/输出量正相关，是 renderer 的主要消耗。
5. 每个会话中继的 36~39MB 私有内存 = node 堆（ssh2 流 + ws + `writeLog` 会话日志缓冲）。

#### 9.3 优化设计（按收益/风险）

| # | 措施 | 收益 | 风险/代价 | 优先级 |
|---|---|---|---|---|
| 1 | **session-server 池化**：一个子进程承载 N 个 SSH 会话（cap 3~5，可配置） | 5 会话 225MB → ~90MB PSS | 隔离性下降：单进程崩溃一损俱损；需重构会话↔进程映射 | 中（收益大） |
| 2 | 会话日志 `writeLog` 可配置关闭/加上限（文件句柄 + 流缓冲） | 每会话省数 MB + 磁盘 IO | 排障能力下降，默认保留 | 低 |
| 3 | xterm `scrollback` 值暴露为设置项并给默认上限 | renderer 私有内存与会话输出量解耦 | 回滚体验变化 | 低 |
| 4 | 测量口径文档化：用 PSS 判断泄漏，RSS 判断峰值 | 消除误判 | 无 | 高（认知纠偏） |

> 注：renderer 进程带 `--disable-gpu-compositing`（无 GPU 环境），xterm 走软件光栅，渲染内存天然偏高——属环境因素。

### 一、内存"大涨大跌"的机理

JS 堆的锯齿形态 = **高频大对象分配 + GC 回收**。分配源是"每次渲染重建的大对象"。数据库页的重渲染频率不低：

- `DbSession` 被 manate `auto` 包裹，订阅其渲染中读过的所有 observable（fullscreen、transfers 进度等）→ 传输期间每帧级重渲染；
- 页面内查找的 MutationObserver → 计数变化触发 setState → 重渲染；
- 任何 store 字段变化都会波及。

所以真正的优化方向是：**把"随渲染重建的大对象"变成"按内容缓存"**。

### 二、热点清单（按影响排序）

| # | 热点 | 位置 | 触发频率 | 影响 | 状态 |
|---|---|---|---|---|---|
| 1 | **值预览高亮每次渲染重算**：放开上限后大值（≤100KB × 全部 ~164 条规则）+ 重建上千个 span，每次渲染都来一遍 | `db-session.jsx` renderRedisDetail | 每渲染 | 🔴 大块内存分配 + 正则 CPU，GC 锯齿的直接来源 | ✅ 已修（§三.1） |

### 三、已实施修复（2026-10-15）

1. **值预览高亮缓存**（主修复）：`highlightedPreview = useMemo(..., [stringValue, activeFormat, keywordPatterns, themeConfig])`——大值高亮只在 值/格式/规则/主题 变化时计算一次，重渲染直接复用缓存的 React 节点，不再每次重建。**上限维持 100KB/2000 命中，不需要改回去**：代价从"每渲染"降为"每次换值一次性"。
2. **`useKeywordPatterns` 改读 `store._config.keywords`**：绕开 deepCopy getter（只读不写，安全），配合已有 `JSON.stringify` 签名依赖，规则不变时零开销。
3. **`themeConfig` 以主题 id 为依赖缓存**：`themeId = store._config.theme` + `useMemo(() => getThemeConfig(), [themeId])`——渲染间身份稳定，主题切换才重算；renderCell 里的对象比较也随之稳定。

> 修复后实测（真实 Redis + CDP）：高亮 span 正常渲染（25 个）；连续切换查找触发重渲染并采样堆 10s：**82 → 82 → 82 → 78 → 78 MB，无增长**。

## 3. 分析：mysql/redis 登录后内存占用（实测取证 + 优化方案）

> 原文档：`分析-mysql-redis登录后内存占用与优化方案-2026-10-16.md`（2026-10-16）

> 背景：用户反馈登录 mysql/redis 后内存偏高（任务管理器总计约 600MB），疑问是"数据量太大导致的正常消耗还是异常"。
> 2026-10-16 完成实测取证（进程对号 + 假 redis 复现），根因落地后整理本文。只含分析与方案，未实施。
> 相关：本文 §2《数据库页性能热点与优化方案》（渲染垃圾/大涨大跌维度，已修复项）。

---

### 一、结论速览

1. **~600MB 总量结构上正常，无泄漏证据**：Electron 多进程基线占大头；主进程空载 RSS 即 ~379MB，与用户实例 386MB 几乎一致——主进程没有随使用异常增长。
2. **根因 A（瞬时放大，可自愈）**：redis 大键详情全量拉取时，主进程经历「RESP 解析 → ioredis 对象 → IPC 结构化克隆」三层拷贝，实测单次 **×5.5**（raw 11MB → anon +60MB），连续操作峰值叠加 ±130MB，GC 后回落。
3. **根因 B（常驻持有，受生命周期控制）**：renderer 把详情全量存入 `redisDetail` state，实测 **×2.4**（+26MB），随换键/关 tab 释放。
4. **坏点确认**：hash `hgetall` / set `smembers` **无任何上限**——"数据量太大"场景的放大器；list/zset 有 1000 上限、mysql/redis 键列表有分页，均受控。
5. **连接生命周期已审计**：常规关闭真实释放（P4，§四）；修复 1 个 open/close 竞态滞留窗口。

### 二、实测取证

#### 2.1 进程对号（用户真实实例，运行 28 分钟；`ps` + `/proc/<pid>/status`）

| 进程 | RSS | 构成 | 说明 |
|---|---|---|---|
| 主进程 | 386MB | RssFile 205 / **RssAnon 仅 40** / Swap 17 | **db 客户端在这里**：`dbClientOp` 走 `ipcMain.handle('async')` → `lib/db-client`（ipc.js:245），mysql 池/redis 客户端/结果 JSON 都在主进程 |
| renderer | 344MB | RssAnon 200 | 终端 scrollback buffer + db 页数据 + 高亮节点 |
| server.js | 68MB | — | **不承载 db 客户端**（纠正最初假设）；纯终端会话在 session-server 子进程（95MB ×2） |
| gpu/utility/zygote | ~130MB | — | 系统组件 |

空载对照：新启动的干净实例主进程 RSS ≈ 379MB ≈ 用户实例 → 主进程无随使用增长；任务管理器 220→378 的"增长"是统计口径差异（PSS/RSS/映射），不是数据泄漏。

#### 2.2 复现实验（假 redis RESP2 + CDP 驱动 `openDbTab`/`getKeyDetail`）

数据集：10 万 field × ~105B 值，raw payload ≈ 11MB。

**主进程侧**（连续 4 次 `getKeyDetail`，间隔 1.5s，按 3s 采样）：

```
baseline         rss=376MB anon=48MB
getKeyDetail#1 → anon +60MB   （≈ raw × 5.5）
#2 → +42MB  #3 → +6MB  #4 → +26MB   （峰值 anon 48 → 180MB）
settle 3×3s   → anon 回落 44MB（rss 373MB）
```

**renderer 侧**（模拟 `redisDetail` state 持有返回结果）：

```
baseline heap used=17MB → hold 后 43MB（+26MB 常驻 ≈ raw × 2.4），8s 稳定
```

#### 2.3 推论

- 主进程增长 = **瞬时放大**（GC 可回收），量级 ∝ 单键数据量；用户切键浏览大 hash 时的锯齿 ±60~130MB 全部来自这里，可自愈、非泄漏。
- renderer 增长 = **常驻持有**，随 `redisDetail` 生命周期释放；加上终端 buffer 构成 renderer anon 200MB 的主体。
- 排除项（实测平稳，非根因）：主进程连接池（`connectionLimit: 4`）、server/session 子进程、渲染层高亮（已 useMemo 化，见性能热点文档）。

### 四、优化方案（按实测根因排序，均未实施）

#### P1 redis hash/set 详情服务端分页（治根因 A+B，收益最大）

- `hgetall` → `hscan(key, cursor, 'COUNT', 500)`；`smembers` → `sscan` 同理；
- server 端协议从 `{ fields, rows }` 扩展为 `{ fields, rows, cursor, hasMore }`（向后兼容：小键一次取完 cursor='0'）；
- renderer 复用现有 `detailLimit`/"load more" 交互，追加"加载下一批（游标）"；
- 同时压掉根因 A（单次 payload 变成 500 条 → 瞬时放大从 60MB 降到 ~0.3MB）和根因 B（常驻持有只有已加载批次）。

#### P2 大 string 值软上限（治根因 A/B 的 string 分支）

- server 端 `GET` 后超阈值（建议 256KB）截断，返回 `truncated: true`；renderer 预览区提示"值过大已截断"；
- 编辑保存需要全量时走单独的 `getFullValue`（或编辑前二次拉取）。

#### P3 `getKeyDetail` 超大键兜底

- 加 `maxFields` 保护（建议 5 万）：超出返回 `truncated: true` + 计数，renderer 提示改用 match 过滤浏览；
- 与 P1 互补：即使未来出现不支持的命令路径，也不会把主进程顶爆。

#### P4 连接生命周期审计（✅ 已审计 + 修复，2026-10-16）

**审计结论：常规路径真实生效**（假 redis socket 连接计数实证）：

| 场景 | 实测 |
|---|---|
| 同 id open→close 循环 ×5 | 每轮连接 1→0，干净归零 |
| 同签名多 tab 共享 | 引用计数共享 1 条连接，最后一个 close 才断开 |
| 调用链覆盖 | delTab/关右/关其他 → `removeTabs` → `closeRemovedDb`；app 退出 → `on-close` → `closeAllDbTabs`；`openDbTab` 同 id 重开先释放 |
| 释放实现 | mysql 引用计数归零 `pool.end()` / redis `disconnect()` / postgres `end()` / `tunnel.close()` |

**发现并修复 1 个竞态滞留**（`db-client/index.js`）：

- 现象：`closeDbTab` 在 `openDbTab` 的 await 完成前到达（`instances` 无正式记录 → no-op），open 完成后连接注册成"无主"→ 滞留到 app 退出/同 id 重开。慢连接（1.5s 延迟模拟）下已复现：conns 卡在 1 不释放。
- 触发条件：慢连接/ssh 隧道（窗口最长 15s OVERALL_TIMEOUT）+ 用户秒关 tab。
- 修复：open 开始注册 pending 占位记录 aborted 标记与中间产物；`closeDbTab` 遇占位置位 aborted；`openDbTab` 在 buildConn 后 / acquire 后 / getMetadata 后分步检查，命中则释放（acquire 成功过才对称 release）并中止；`dbClientOp`/`setDbReadOnly` 对占位按"未打开"处理。修复后复测：close 后 conns 1→0，open 返回 rejected。
- 残留边界（记录不动）：renderer 崩溃时主进程感知不到（连接挂到 app 退出）；慢连接下 `dbClientOp` 在 open 完成前到达会得到 "database tab not open"（原有行为）。

#### P5 观测型优化（等证据，暂不动）

- 网格 dataSource useMemo、renderCell 高亮 LRU（原《数据库页性能热点》§四.1/§四.2）——解决渲染垃圾而非稳态占用；
- 仅当用户改大 pageSize（1000 行 × 高亮）且观测到渲染卡顿时再做。

### 五、"正常还是异常"判定标准（给使用者的口径）

- **正常**：浏览大 hash/set 后内存上涨 → 稳定平台 → GC/切键回落（涨后平台 + 锯齿是 V8 常态）；关 tab 后回落。
- **异常**（满足任一）：①反复切键/翻页内存阶梯式上涨不回落；②关闭数据库 tab 后不释放；③空载数小时线性增长。

按此口径，当前实例属于**正常**；P1/P2/P3 实施后，大数据量场景的峰值与常驻都会降到与数据量成比例的可控范围。
