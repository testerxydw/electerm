# 分析：数据库页性能热点与优化方案（内存大涨大跌）

> 背景：用户反馈运行中的 electerm 内存不稳定、大涨大跌，怀疑与「值预览高亮放开上限」有关（2026-10-15 `e3902a74`）。
> 本文分析热点、定性已实施修复，并登记未实施的后续优化项。
> 状态：§三 1~3 已实施（同日提交）· 其余待排期

---

## 一、内存"大涨大跌"的机理

JS 堆的锯齿形态 = **高频大对象分配 + GC 回收**。分配源是"每次渲染重建的大对象"。数据库页的重渲染频率不低：

- `DbSession` 被 manate `auto` 包裹，订阅其渲染中读过的所有 observable（fullscreen、transfers 进度等）→ 传输期间每帧级重渲染；
- 页面内查找的 MutationObserver → 计数变化触发 setState → 重渲染；
- 任何 store 字段变化都会波及。

所以真正的优化方向是：**把"随渲染重建的大对象"变成"按内容缓存"**。

## 三、已实施修复（2026-10-15）

1. **值预览高亮缓存**（主修复）：`highlightedPreview = useMemo(..., [stringValue, activeFormat, keywordPatterns, themeConfig])`——大值高亮只在 值/格式/规则/主题 变化时计算一次，重渲染直接复用缓存的 React 节点，不再每次重建。**上限维持 100KB/2000 命中，不需要改回去**：代价从"每渲染"降为"每次换值一次性"。
2. **`useKeywordPatterns` 改读 `store._config.keywords`**：绕开 deepCopy getter（只读不写，安全），配合已有 `JSON.stringify` 签名依赖，规则不变时零开销。
3. **`themeConfig` 以主题 id 为依赖缓存**：`themeId = store._config.theme` + `useMemo(() => getThemeConfig(), [themeId])`——渲染间身份稳定，主题切换才重算；renderCell 里的对象比较也随之稳定。

> 修复后实测（真实 Redis + CDP）：高亮 span 正常渲染（25 个）；连续切换查找触发重渲染并采样堆 10s：**82 → 82 → 82 → 78 → 78 MB，无增长**。

## 四、后续优化（未实施，按需排期）

| # | 项 | 建议 | 优先级 |
|---|---|---|---|
| 1 | 网格全量重渲染：`grid.rows.map` 每次 render 生成新 dataSource 数组 → antd Table 全行重渲染 | dataSource 用 useMemo（依赖 grid.rows / editing / 只读等实际输入）；更进一步可把行组件 memo 化 | 中（传输期间打开大表时最明显） |
| 2 | renderCell 逐格正则：可加"文本→高亮结果"的 LRU 缓存（单元格文本重复率高时收益大） | 低成本，观测到卡顿再做 | 低 |
| 3 | `store.config` deepCopy getter 的系统性风险 | 性能敏感路径一律读 `_config`（只读）或局部缓存；把这条写进代码注释惯例 | 中（防复发） |
| 4 | MySQL 元数据 N+1 / 系统库过滤 | 见 TODO「DB 遗留缺口」P1-7 | 中 |
| 5 | 终端侧同款审计：`store.config` getter 在终端组件里的每渲染调用点 | 与本文同方法论，单独立项 | 低 |

## 五、一句话

高亮放开本身不是错，错在"每次渲染都重算+重建"——已用 useMemo 把代价锁到"换值时一次"，并顺手消掉了 config deepCopy / themeConfig 重建两个每渲染垃圾源；实测堆曲线平稳。若仍观察到波动，优先排查传输进度等高频 store 更新引发的网格全量重渲染（§四.1）。
