# 分析-资源优化与前端框架评估-2026-11-10

> 触发：用户要求「前端框架更换探索」，约束为**降低资源占用、不降低多端适配**。
> 多端范围（实测盘点）：Win/macOS/Linux 多 OS；x64/arm64/**loong64（龙芯）/ppc64le** 架构
> （`src/build/bin/build-linux-arm*`、`build-linux-loong64.js`、`src/build/ppc64le/`）；
> `web-app/` Web 版形态；`is-mobile` 移动布局；legacy Electron<25 polyfill 分支。

## 0. 结论速览

| 议题 | 结论 | 依据 |
|---|---|---|
| 换 UI 框架（Vue/Svelte/Solid） | **不做** | 资源收益 5-10%，多端风险极高（§3） |
| 换组件库 | **不做** | 痛点源是运行时样式注入模式，多数现代库同款 |
| 打包瘦身 | **已执行，-5MB** | `prune-node-modules.js`（§4） |
| antd6 cssinjs 完全静态化 | **不可行** | 动态自定义主题是产品能力（§5） |
| antd6 cssVar 模式 | **可选优化**，非资源刚需 | 切主题零重注入，工作量小（§5） |
| 懒加载再收口 | **优先级低** | 会话级+SQL 编辑器级 lazy 已收口（§6） |
| redis 控制台双滚动条 | **已修复**（本日） | 根因非 SSOT 失效，见 §7 |

## 2. 框架更换三路线评估

| | A. 留 React+antd + 资源专项 | B. 换组件库 | C. 换 UI 框架 |
|---|---|---|---|
| 资源收益 | **15-30% 内存**（Electron/xterm 侧） | ≈0 | 5-10%（相对 Electron 基线） |
| 多端风险 | **零** | 中（loong64/ppc64le 构建链重验） | **极高**：五端测试矩阵重验、构建链（lightningcss 仅 x64 二进制、@rolldown native）、web-app 同套代码需重写、webgl circuit-breaker 重搭 |
| 改动面 | 打包脚本+CSS 治理 | 263 文件 + 121 处 `.ant-` 样式覆盖 + 35 种组件等价性 | 289+263 文件 ≈ 13 万行 UI 层 |
| 周期 | 天级 | 月级 | 人年级 |

**框架无关的可复用资产**（换栈时保留，也是「不换」的理由之一）：状态层 30 个 store 文件仅 1 个 import react；`@electerm/xterm` fork 框架无关；109 个 CDP 探针量 DOM 不关心框架。

## 3. 已执行：打包瘦身（-5MB）

**根因**：`build-deb-fast` 增量路径不重跑 `prepare.js`（work/app 只首次准备），依赖更新后 `npm i` 把浏览器构建冗余重新带进产物（axios/dist 残留即证）。

**方案**：新建 `src/build/bin/prune-node-modules.js` 幂等清理模块，`prepare.js` 与 `build-deb-fast.js`（asar 打包前，第 5.5 步）共用同一清单。

| 清理项 | 体积 | 入口依据（只删 require 解析不可达） |
|---|---|---|
| `node-forge/dist` | 604K | main=lib/index.js，包无 exports 字段 |
| `pako/dist` | 484K | exports["."].require=index.js；dist 仅显式子路径可达（源码无引用） |
| `trzsz2/dist/browser` | 180K | exports["."].require=dist/cjs-full/index.cjs |
| `sm-crypto-v2/miniprogram_dist` | 172K+ | main=dist/index.js；小程序构建 |
| `axios/dist/{esm,browser,*.js,*.map}`、`index.d.cts`、`lib` | ~400K | main=dist/node/axios.cjs（原 prepare.js 清理收编） |
| node-pty 对端平台文件/测试文件 | — | 原生 .node 由 electron-rebuild 只构建本平台 |

**保留**：`@electerm/electerm-themes/dist`（main 即指向）、`aws-ssl-profiles` CA 表（mysql2 运行时用）。

**实现要点**：删除必须走 `rmForce`（fs.rmSync → 原生 `/bin/rm` 兜底）——本机 node 安全 shim 会拦 shelljs rm（deb-fast 注释同款坑，实测踩中）；失败只警告不中断打包。多端安全：node-pty 清理按 `process.platform` 判定对端，所有架构同逻辑。

**验证**：五包入口 `require` 全部 OK；node_modules 70MB→65MB；lint 0。

## 4. 深度分析：antd6 cssinjs 静态化

**现状**（`store.js:344-370`）：`uiThemeConfig` 的 token 全部来自用户主题运行时取值（`themeConf.primary/main/error/...`），`algorithm` 按 `isColorDark(themeConf.main)` 动态切换亮/暗。

**结论**：
- **完全静态化（static-style-extract / 编译期提取）不可行**——会把「用户自定义主题 + 亮暗动态切换」砍掉，这是产品能力不是实现细节。
- **cssVar 模式可选**（`ConfigProvider theme={{ cssVar: true }}`）：token 转 CSS 变量，组件样式只注入一次、切主题只改变量值。兼容性无虞（CSS 变量 Chrome 49+，legacy 分支 Electron 22 = Chrome 108）。收益是切主题流畅度与少量 style 标签内存，**非资源刚需**，建议与暗色切换卡顿优化合并做。
- **重要事实记录**（纠正一次误判）：antd6 默认 `hashPriority:'low'`，hashId 注入形态为 **`:where(.css-hash)`，`:where()` 特异性为 0**（`@ant-design/cssinjs/es/util/index.js:145`）——因此 antd6 运行时规则有效特异性仍是 0,1,0，**SSOT 的 `!important` 覆盖不受压制**。全局探针 74/74 PASS 佐证。此前「hashId 特异性压制 SSOT」的假设**不成立**。

## 5. 深度分析：懒加载收口

- 主 bundle 636KB；`db-session`/`web-session`/`spice-session`/`SqlCodeEditor`（codemirror 376K）**全部已是 React.lazy 按需 chunk**（主 bundle 的 `import()` 动态引用实测确认）；24MB 是全量 chunk 磁盘体积，非内存。
- `db-session.jsx` 4826 行 / 104 个 import：可再按低频子功能（ER 图、结构对比、SQL AI）拆动态 import，收益仅为首次进入数据库功能的本地 IO+解析（几十 ms 量级）。
- `conf.js:64` 的 `codeSplitting: false` 字段与实际产物（chunk 正常分割）矛盾，疑为 rolldown-vite 无效/旧字段，值得核对但不阻塞。
- **结论：架构已良好，无高收益收口点，优先级低。**

## 6. 附：redis 命令控制台双滚动条（根因 + 修复，本日完成）

**现象**（用户截图）：命令控制台弹层右缘两条滚动条并排。

**排查链**：
1. 全局 SSOT 探针 74/74 PASS + `:where()` 特异性证据 → 排除「antd6 压制 SSOT」的全局失效假设。
2. 新增定向探针 `self-test/db-redis-console-scroll-probe.js`（Xvfb+CDP 实机；**需本机 redis**——连接失败态不渲染键空间工具条，本机已 `apt install redis-server` 8.0.2 解决）实测复现：

| 层 | 修复前 | 修复后 |
|---|---|---|
| `.ant-modal-body` | **sh 309 > ch 210（滚动条）** | **sh 432 = ch 432（无滚动条）** |
| `.db-redis-console-suggest` | sh 749 > ch 218（自滚，合法） | 同左（唯一滚动层） |
| 判据 | 弹层内可滚元素 2 → **FAIL** | ≤1 → **9/9 PASS** |

**根因**：`.db-redis-console-suggest` 曾为 `position:absolute`（`top:100%` 相对 sticky 输入行）。**absolute 溢出后代计入最近滚动容器（`.ant-modal-body`）的 scrollHeight**——浮层一展开，body 即被撑出「假溢出」滚动条，与浮层自身滚动条并排贴在右缘。

**修复**（治本，非样式遮盖）：
- `db-redis-console.jsx`：suggest 块从 flex 输入行内移出，置于输入行之后、历史之前（文档流）。
- `db-session.styl`：`.db-redis-console-suggest` 去 `absolute/top/left/right/z-index`，注释记录权衡（放弃「弹层高度不跳动」诉求：跳幅 ≤220px 换双滚动条根除）。
- spec 同步：`db-redis-console-ui.spec.js` 补全列表断言反向锁定 `position absolute`（防回归）。

**验证**：定向探针 9/9 PASS；全局探针 74/74；test-unit-ci 全绿；lint 0。

## 8. 换桌面容器框架（Electron → Tauri 等）可行性评估

> 追加于 2026-11-10。问题：不用 Electron、换大框架，运行资源与打包体积能否均减小？
> 结论先行：**是唯一能同时大幅砍体积（-60~70%）和内存（-50~150MB）的路线，且本项目后端架构恰好为此做了多年铺垫；但 ppc64le/loong64 是决定性红线，多端矩阵不收缩则不可行。**

### 8.1 实测架构事实（决定可行性走向）

| 事实 | 实测数据 | 含义 |
|------|---------|------|
| Node 后端总规模 | `src/app` 204 文件 / **4.85 万行** | 若用 Rust/Go 重写 = 人年级，直接否决重写路线 |
| **协议层零 Electron 耦合** | session-ssh/sftp/ftp/telnet/serial/rdp/vnc/spice/zmodem/trzsz/tunnel/hop 全在 `src/app/server/`，**无一 require electron** | 协议层可整体搬运 |
| **web 后端已独立存在** | `src/app/server/server.js`：express + ws，web-app 形态已生产运行 | 「Node 后端作为独立进程」不是假设，是既成事实 |
| Electron 耦合仅容器层 | `src/app/lib` 仅 **15 个文件** require electron（window/ipc/menu/deep-link/safe-storage 等） | 换容器只需重写这层（本来就要换掉的东西） |
| IPC 面很小 | `ipcMain.handle/on` 仅 7 处，客户端 invoke 3 处 | IPC 重写成本低 |
| 原生模块 | node-pty 1.2.0-beta.15、serialport 13、@electerm/ssh2 定制 fork | 交叉编译 5 端的现状不变 |
| UI 层 | React 13.3 万行 + xterm fork，容器无关 | 整体保留 |

### 8.2 唯一可行路线：Tauri 壳 + Node sidecar（后端零重写）

```
Tauri(Rust 壳, 系统WebView)          ←≈5-10MB，替代 Electron 的窗口/菜单/托盘/自动升级
  └─ spawn: 现有 Node 后端(sidecar)   ←src/app/server 原样打包，express+ws 通信
       └─ React UI                    ←既有前端经本地 ws 连 sidecar（web-app 同款链路）
```

**为什么是 sidecar 而非 Rust 重写后端**：4.85 万行 ssh/vnc/rdp/serial 协议代码用 Rust 重写（russh/portable-pty/serialport-rs）行为级等价（加密协商、跳板、keepalive、zmodem 边角）为人年级风险；而 web-app 形态已经验证了「独立 Node 后端 + 浏览器前端」全链路。Tauri v2 原生支持 sidecar 外置进程。

**体积/内存账（对比实测基线）**：

| 项 | 现状(Electron 44) | Tauri+sidecar | 差值 |
|---|---|---|---|
| 安装体积 | ~284MB | Rust壳 5-10 + React 产物 ~24 + Node 二进制 ~45 + 精简 node_modules ~15-25 | **~90-105MB（-60~70%）** |
| 常驻内存 | Chromium 独立进程基线 ~150-250MB | 系统 WebView（与 OS 共享浏览器栈）+ Node sidecar | **约 -50~150MB** |
| 启动 | Chromium 冷启 | WebView 冷启更快 | 小幅 |

注：纯 Rust 重写后端（不带 Node）可达 ~30-40MB，但代价如上（人年级）不采。

### 8.3 风险矩阵（红线判定）

| 风险 | 等级 | 说明 |
|------|------|------|
| **ppc64le/loong64 的 WebKitGTK** | 🔴 决定性 | Tauri 官方仅出 x64/arm64 预编译。Electron 自带 Chromium，「从源码构建」项目已趟过（`src/build/ppc64le/` 补丁体系）；WebKitGTK 从源码构建的依赖树远比 Electron 大，且系统 WebView **版本碎片化不可控**——Electron 的「大」恰恰是多端渲染一致性的来源 |
| Windows WebView2 | 🟡 低 | Win10 1809+ 系统自带；更老系统本就不在 Electron 44 支持范围 |
| sidecar 生命周期管理 | 🟡 中 | 自升级/崩溃重启/单实例/safe-storage（keytar→Tauri stronghold）等 15 个 lib 文件的等价替换 |
| node-pty/serialport 交叉编译 | 🟢 不变 | 与现状相同（electron-builder 已在做） |
| 前端回归 | 🟢 低 | React/xterm 层不动；CDP 探针体系改连 WebView 后可复用 |

### 8.4 结论与决策条件

- **若多端矩阵必须保留 ppc64le/loong64（红线不收缩）→ 换容器不可行**。Electron 是国产架构上唯一被验证的「自带一致渲染栈」，这条没有被更小的框架填补。
- **若多端可收缩至 x64/arm64（+独立 web 形态）→ Tauri + Node sidecar 是正确路线**：体积 -60~70%、内存 -50~150MB，工作量约 **2-3 人月**（15 个容器层文件重写 + sidecar 进程治理 + 双端打包链），期间功能冻结。
- **无论决策如何，前置工程都值得做（半步走）**：把桌面版前端通信从 Electron IPC 迁到「本地 server + ws」与 web-app 完全同构。该步独立有价值（桌面/容器/web 三形态一套通信协议），完成后再评估换壳，届时壳层替换风险从「架构级」降为「装配级」，且随时可回退。

## 9. Rust 全栈路线深度评估（用户意向：用 Rust）

> 追加于 2026-11-10。问题：不用 Electron、后端也 Rust 化（彻底去 Node），可行性与代价？
> 结论先行：**技术可行，生态覆盖超预期（唯一缺口 trzsz 需 757 行移植）；收益比 Node sidecar 再砍 ~60MB 体积 + ~50MB 内存；但工作量是 sidecar 路线的 3-4 倍（6-10 人月 vs 2-3），且换壳的多端红线（§8.3）依旧独立存在——好在 Rust 后端与换壳是两个可拆解的决策。**

### 9.1 重写面盘点：4.85 万行 Node 的 Rust 生态对照（实测）

**协议层 `src/app/server/`（1.48 万行）**：

| 模块 | 行数 | Rust 对应 | 生态成熟度 |
|---|---|---|---|
| session-ssh.js | 1588 | **russh**（wezterm/Tabby 在用） | ✅ 成熟 |
| zmodem.js | 1259 | **zmodem2 crate**（async API，2025 活跃）/ rzsz crate | ✅ 有生态 |
| rdp-proxy + session-rdp | 1242 | **已是 IronRDP WASM + 服务端 TLS 中继**；IronRDP 本就是 Rust 项目 | ✅ 极低（中继=纯 IO 转发） |
| xmodem.js | 940 | rzsz crate（X/Y/ZModem 全套） | ✅ 有生态 |
| session-server.js | 778 | axum + tokio-tungstenite | ✅ 成熟 |
| trzsz.js | 757 | **无官方 Rust 实现**（官方仅 JS/Go 版 trzsz-go） | ⚠️ 唯一缺口，需参考 Go 版移植 |
| session-sftp.js | 721 | russh-sftp | ✅ 成熟 |
| ssh-known-hosts | 560 | russh 内置 known_hosts | ✅ |
| telnet.js | 485 | 自研状态机（纯逻辑） | 🔧 小型移植 |
| spice-proxy + session-spice/vnc | ~630 | socket 中继（tokio TCP relay） | ✅ 极低 |
| transfer/ftp/ssh-tunnel/hop 等 | ~2500 | suppaftp / russh 原生跳板 | ✅ |
| webdav-sync | 260 | reqwest_dav | ✅ |

**关键发现（降低难度的三个事实）**：
1. RDP 走「IronRDP WASM 浏览器渲染 + 服务端 RDCleanPath 中继」——协议逻辑在浏览器，服务端 1242 行只是 TLS 握手 + 双向转发，tokio 重写是玩具级；
2. VNC/SPICE 同构（服务端纯 socket 中继）；
3. zmodem/xmodem 有活跃 Rust crate（zmodem2 async API、rzsz 含 CRC/断点续传/多文件批传），@electerm/ssh2 fork 的算法配置在 `ssh2-alg.js` 是**声明式导出**（SUPPORTED_KEX/CIPHER/MAC），russh 同样声明式可对齐。

**公共层 `src/app/common + migrate`（6560 行）**：log→tracing、nedb→sled/redb（含数据迁移）、配置→serde。
**容器层 `src/app/lib`（15 文件）**：Tauri 原生能力覆盖大半（updater/menu/deep-link），safe-storage→keyring crate。

### 9.2 收益对比（vs §8.2 的 Node sidecar）

| 项 | Electron 现状 | Tauri+Node sidecar | **Tauri+Rust 后端** |
|---|---|---|---|
| 安装体积 | ~284MB | ~90-105MB | **~30-40MB（-85%）** |
| 后端常驻内存 | V8 独立进程 | Node sidecar ~50-80MB | **Rust ~10-20MB** |
| 运行时依赖 | Chromium+Node | +Node 二进制 | 无（单静态二进制） |
| GC 抖动/冷启 | 有/中 | 有/中 | 无/快 |
| 交叉编译 | electron 源码构建（已趟通） | Node 官方多架构二进制 | **rustc 官方支持 ppc64le/loong64 target（tier2），musl 静态编译** |

### 9.3 成本与风险

| 项 | 等级 | 说明 |
|---|---|---|
| 工作量 | 🔴 | 协议层 1.5万行 JS→Rust ≈ 4-6 人月；common 1-1.5 人月；壳集成 0.5-1 人月；互操作回归 1-2 人月（可并行）。**合计 6-10 人月，为 sidecar 路线（2-3 人月）的 3-4 倍** |
| SSH 老设备兼容 | 🟡 | russh 算法声明式可配，但 @electerm/ssh2 fork 存在本身说明历史上有设备踩过坑——KEX/CIPHER 逐项对齐 + 老设备回归是刚需（存储设备场景老算法常见） |
| trzsz 移植 | 🟡 | 757 行参考官方 Go 版重写，协议确定性高；与旧版对端互操作需真机回归 |
| 开发体验变化 | 🟡 | Node「npm start 即测」→ Rust 编译周期 + borrow checker 摩擦；快速迭代节奏受影响（可用 cargo watch + hot reload 缓解） |
| 换壳多端红线 | 🔴 不变 | §8.3 的 ppc64le/loong64 WebKitGTK 问题**与后端语言无关**，依旧存在 |

### 9.4 关键洞察：Rust 化与换壳是两个独立决策（可拆解、可回退）

```
Phase 0（已论证）: 桌面 IPC → 本地 server+ws 同构         ← 独立价值，随时可停
Phase 1: Rust 重写 ssh/sftp/pty（crate 最成熟），以 sidecar 接入**现有 Electron**
         ← 不换壳、不动 UI；协议等价性在真实环境（HSM 设备）逐项验证
Phase 2: Rust 化 zmodem/xmodem/trzsz + common → 全后端 Rust，Node 退役
         ← 此时 Electron 壳 + Rust 后端已是稳定形态，ppc64le/loong64 不受影响
Phase 3（可选）: 主流 x64/arm64 换 Tauri 壳（30-40MB 达成）
         ppc64le/loong64: 继续用 Electron+Rust 后端（sidecar），或引导走 web 形态
         ← 壳层替换风险已从「架构级」降为「装配级」
```

**Phase 1 的特殊价值**：rustc 对 ppc64le/loong64 是官方 tier2 target（musl 静态编译），Rust 后端二进制可在国产架构上直接交叉编译——**后端 Rust 化对多端是利好而非风险**；风险全部集中在「壳」（WebKitGTK），而壳的替换被推迟到 Phase 3 且可不做。

### 9.5 判定

- **纯技术**：可行，生态覆盖 ~95%（唯一缺口 trzsz 757 行），RDP/VNC/SPICE 因现有架构反而更简单。
- **收益**：终极形态 ~30-40MB / 内存大降 / 单二进制——比 sidecar 多赚 60MB 体积 + 50MB 内存。
- **代价**：6-10 人月 vs 2-3 人月，SSH 老设备回归是质量关键路径。
- **建议**：若确定走 Rust，按 §9.4 分阶段——Phase 0/1 立即启动（零风险、独立价值），Phase 3 换壳与否在 Phase 2 完成后再决策，届时信息最全。
